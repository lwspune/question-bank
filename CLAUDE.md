## Multi-tenancy + visibility model

**Platform brand vs. tenant org-name — do NOT conflate (and don't "purge" `"LWS Pune"`).** The public brand is **PYQ Vault** (`SITE_NAME` in `layout.tsx`; Footer, JSON-LD publisher, all anon/student-facing copy) — that's what everyone sees. Separately, **`organizations.name` is tenant data**, and `"LWS Pune"` is the **founding org customer (tenant #1)** that owns the seeded content. An org name is rendered ONLY on staff-gated surfaces (AppHeader, `/dashboard/*`, `/uploads`, `/account`, `/papers`) — always behind a `member` (`org_members` row), so **anon + self-serve students never see it**. When a second school onboards, they get their own org row and *their* staff see *their* name; nobody's org name is ever the public brand. Consequently the `"LWS Pune"` string in `api/sync/mock/route.ts` (`DESTINATION_ORG_NAME`), `tests/global-teardown-helpers.ts` (`REAL_ORG_NAMES`), the DB-integration tests' `.eq("name","LWS Pune")`, and scripts' `sourceFile`/`pyqNote` provenance are all **correct as-is** — legitimate tenant identity + attribution, NOT stale branding. A public-facing `LWS` literal (hardcoded in JSX/copy, not read from the org row) IS a branding bug → use PYQ Vault / "our team" (the 2026-07-12 sweep already fixed the known set). Rule of thumb: reads from `organizations.name` / routes by org identity → keep; hardcoded brand string shown to the public → PYQ Vault.

Per-school orgs, RLS-enforced. **Role model overhauled 2026-07-15 (migrations 0055–0057) — content editing collapsed to superadmin-only; teachers became branch-scoped paper-builders. The old "ADMIN does everything / TEACHER edits content" (migration 0025) is SUPERSEDED — see [[project-member-management]].**
- **Service role** (seed + ingestion scripts, server-only admin actions) bypasses RLS by design — never expose to client code. **The primary content add/edit path** — the whole bank is built here.
- **SUPERADMIN** (platform staff above orgs — `platform_admins` table, migration 0056; seeded = `connect.lwspune@gmail.com`) — the ONLY identity that can add/edit question CONTENT (questions/options/taxonomy/tags/embeddings/uploads), across ALL orgs. Cross-org console at `/superadmin` (list orgs · onboard a new org · provision its admins/teachers). NOT an `org_members` row; detected via `getSessionSuperadmin()`/`requireSuperadmin()` (service-role read of `platform_admins`).
- **ADMIN** — own-org *management*: create branches + teachers, assign teachers to branches, build papers, triage reports, manage members + entitlements. **Cannot add/edit content** (superadmin-only since 0056).
- **TEACHER** — assigned branch(es) ONLY: read the bank + build papers/batches for their branches (with the per-batch no-repeat warning). Branch-scoped via `branch_members` (0057). **Cannot edit content**, manage members, or manage branches.
- **anon** (no JWT) can read PUBLIC questions/options + all taxonomy. Cannot write anything.
- **STUDENT** (signed-in, self-serve, **no `org_members` row** — added 2026-06-01) registers at `/signup` (Google OAuth or email/password). By RLS construction they get zero private data; what an account unlocks is in-app question reports today + premium content via the entitlement axis below. Org-less = student (admins always get an `org_members` row atomically), so `/dashboard` redirects them to `/browse`.

**Cohorts: Org → Branch → Batch (migrations 0054/0055).** A **branch** (`branches`, admin-managed) is a campus (e.g. "FC Road"); a **batch** (`batches`) is a cohort ("NDA 2026 Morning") filed under a branch; a **paper** optionally targets a batch. The point of batches: the paper builder soft-warns when a question was already used for the SAME batch (per-batch non-repetition, derived from `paper_questions` joined to `papers.batch_id`; scope = per-batch, enforcement = soft-warn). Teachers are scoped to their `branch_members` branches for batches/papers; admins see all org papers; collaboration is branch-mediated. See [[project-member-management]].

**Premium entitlement axis (orthogonal to orgs, migration 0026).** Paid/comped access lives in `public.entitlements`, keyed on `auth.users(id)` — NOT org-scoped, because a student has no org. A grant unlocks a `scope` ('all' = full premium); `source` ∈ `razorpay | comp | manual` (the gate is **source-agnostic** — `userHasAccess` just asks "active entitlement for this scope?"; staff/org-members bypass the paywall). Writes are **service-role only** (no write RLS); reads are own-row only. Consumers: the `/notes` preview-gate (`tier:"paid"` chapters), `/pricing`/`/account`, the Razorpay webhook, and the `/dashboard/entitlements` comp UI. See the 2026-06-01 Decisions log entry + [[project-paywall-build]].

Each question has a `visibility` enum (`PUBLIC | PRIVATE`, default **PUBLIC** as of migration 0022 / 2026-05-17 — was PRIVATE prior). Read RLS is the union of two permissive policies: `(visibility = 'PUBLIC')` for everyone, plus `(org_id = private.current_user_org_id())` for authenticated org members on their own org's PRIVATE rows. Authenticated users see PUBLIC across all orgs + their own PRIVATE; anon sees only PUBLIC. Admins flip per-question visibility from the edit page.

Each question also has a **`question_kind` enum** (`pyq | practice`, default `pyq`, migration 0036) — the axis that separates the past-year corpus from the supplementary **practice** bank (the product is PYQ-first; **3,040 practice q live across 29 NDA Maths chapters as of 2026-06-13 — ALL 5 source folders ingested (Algebra + Trigonometry + Calculus + 2D Geometry + 3D Geometry; the 3D folder fed both the Vectors and 3D Geometry chapters)**, separate from the PYQ counts above). `/browse` exposes it as a **PYQ / Practice / All** toggle (default PYQ; `kind` filter in [filters.ts](src/lib/questions/filters.ts) → `query.ts` + `p_kind` on the facet RPCs). PYQ-only surfaces stay clean two ways: **tag-gated** surfaces (guide principles, notes drills, worked examples, quiz harvest) are PYQ-only *by construction* (practice questions are never principle/concept-tagged — doing so would leak them in), while the four **raw count-by-taxonomy** queries (`examHomeStats` + the 3 notes landings) carry an explicit `question_kind='pyq'` guard. Practice ingestion is its own pipeline + runbook — see [[practice-ingestion]] + `scripts/practice/README.md`.

Each question also has a **`question_format` enum** (`mcq | subjective`, default `mcq`, migration 0041) — the axis separating standard MCQs (4 options, exactly one `is_correct`) from **subjective/free-response** questions (State Board textbook content), which carry **zero option rows** and whose model answer lives in `questions.solution`. Subjective support: `subjectiveContentHash(stem, context)` in [hash.ts](src/lib/upload/hash.ts) (namespaced so it can't collide with an MCQ; context-aware so set-based siblings with the same bare sub-item text don't dedup-collide; excludes `solution` so answer-backfill doesn't change the id); `commitStaged` writes `question_format` + emits no options for subjective; `/browse` QuestionCard renders subjective as stem + "Show model answer" (no A–D); the Word answer-key prints the model answer instead of `(?)`. `question_format` is optional on the `QuestionRow` view-model (absent ⇒ MCQ). **Deferred (non-critical — no subjective content reaches them by construction):** a `/browse` format-filter toggle, subjective in the admin edit *form* (answers are backfilled by script, not the UI), and quiz-harvest / RAG one-correct-option guards. See [[state-board-ingestion]].

RLS helpers live in the **`private` schema** (not exposed by PostgREST): `current_user_org_id()`, `current_user_is_admin()`, `current_user_is_superadmin()` (0056), `current_user_can_edit_content()` (0056), `current_user_can_edit_questions()`, `current_user_branch_ids()` (0057). **The semantic split matters (0056):** `can_edit_content()` = **superadmin-only**, gates all CONTENT writes (questions/options/taxonomy/tags/embeddings/uploads); `can_edit_questions()` is UNCHANGED (admin OR teacher) and now gates **paper/batch building** ONLY (papers/batches/paper_questions), NOT content — do not conflate them (redefining `can_edit_questions` would break the paper builder). Use `current_user_is_admin()` for org-management (branches, members, reports triage, entitlements); `current_user_branch_ids()` scopes a teacher's batches/papers to their assigned branches.

## Commands

```sh
npm run dev                # next dev (local)
npm run build              # production build
npm run lint
npm run typecheck          # tsc --noEmit (covers test files too — keep this clean)
npm test                   # vitest run
npm run test:watch
npm run db:seed            # idempotent taxonomy seed (service-role)
npm run extract:taxonomy   # regenerate supabase/seed/taxonomy.json from a reference Excel
npm run notes:lint         # validate /notes editorial modules against live taxonomy + DB tags (read-only)
npm run notes:latex        # audit /notes for LaTeX-in-plain-text leaks + delimiter imbalance + unicode (read-only)
npm run notes:order        # populate subtopics.order_index from each /notes chapter's subtopicOrder (teaching order on /browse); --dry previews
npm run notes:coverage [subjectRoute] [chapterSlug]  # triage probe: math in a chapter's PUBLIC solutions but NOT in its notes (formula-gap candidates); default nda-maths statistics. Noisy — human-review list, not a gate
npm run tags:audit         # principle-tag audit (read-only)
npm run audit:underlines   # scan PUBLIC questions for \underline{...} segments not covered by the docx-export bypass
# — Daily Quiz Factory (see Decisions log 2026-06-08 + [[daily-quiz-pilot]] memory) —
npm run quiz:harvest [route/chapter ...]   # /notes ConceptUnits → MCQ atoms JSON (scripts/quiz/atoms/*.json); default 3 sample chapters
npm run quiz:sync          # upsert harvested atoms → public.quiz_atoms (staleness-aware: preserves verified, re-flags changed)
npm run quiz:verify [name] # promote needs_review atoms → 'verified' from scripts/quiz/verify/<name>.ts (Claude-authored distractors)
npm run quiz:lint [route] [chapter]   # flag quiz-atom stems that aren't self-contained (back-refs, criterion-less "which is correct?", fragments, generic auto-harvest "formula for <X>?" template) — paginates the full ready pool; triage, run before publishing a quiz public
npm run quiz:coverage [route] [chapter] [--review]   # flag formulas/traps TAUGHT in /notes prose but not harvestable (formula.latex empty / <12 traps) — the theme-coverage guardrail; triage, not a gate
npm run quiz:assemble <route> <chapter> [max] [size] [-- --theme=X]   # ready atoms → quiz → record (quizzes+map) → push nda-tracker draft
npm run quiz:delete <slug>   # delete an assembled quiz here + propagate the delete to nda-tracker (drafts only there)
npm run quiz:push [daily/<slug>]   # push a single DraftQuiz module to nda-tracker (default: the hand-authored classical quiz)
npm run stats              # report live bank size (PUBLIC by exam/subject) + taxonomy + /notes chapter & diagram counts — for verifying the header lines instead of hand-maintaining them
npm run board:lint         # /board section-structure gate: fails if a PUBLIC board (question_kind='practice') row lacks section_* fields or a chapter's section_seq isn't contiguous 1..N (scripts/stateboard/lint-sections.ts)
npm run db:types           # supabase gen types (requires SUPABASE_PROJECT_REF env)
npm run prepush            # the chained gate, MIRRORS CI: typecheck → lint → notes:lint → notes:latex → test → build; run by .githooks/pre-push
npm run gate [target]      # wrapper that runs `npm run <target>` (default prepush) and prints a GATE_RESULT: PASS/FAIL sentinel as its LAST line — so the result survives `| tail` even though a pipe masks the exit code
```

> **Pre-push gate.** `.githooks/pre-push` runs `npm run prepush` before any push — which now **mirrors CI exactly**: typecheck → lint → notes:lint → notes:latex → **test** → build (single source of truth: the `prepush` script). So a green pre-push means a green CI. Widened 2026-06-02 from the old build-only chain after a broken test passed pre-push and only failed in CI (it didn't run `npm test`). Cost: ~3–4 min (full suite + build). Activated by the `prepare` script (`git config core.hooksPath .githooks`) on `npm install`. `.gitattributes` pins LF on `.githooks/*` so the shebang resolves on Linux/WSL contributors. Escape hatch for WIP pushes: `git push --no-verify` — don't reach for it unless you know why.

> **CI gate.** `.github/workflows/ci.yml` runs the **full** gate (typecheck → lint → `notes:lint` → `notes:latex` → `npm test` → build) on every push to `main` + every PR. The local pre-push hook now runs this same chain (see Pre-push gate above), so CI is a backstop rather than the first place these checks run — it still matters because it runs on a clean checkout with repo secrets even if someone `--no-verify`s. Requires three repo secrets (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`); without them the build + DB steps fail and the DB tests skip. Runs against the single prod Supabase project (test rows auto-swept by `global-teardown`) — point the secrets at a staging project if write traffic gets noisy. Vercel still owns deploys; CI is the correctness gate.

## Conventions specific to this project

- **Spacing scale.** Page wrappers `p-8`, content cards (CardContent default) `p-6`, compact cards (FilterBar etc.) `p-4`, nested option blocks `p-3`. Pick the smallest tier that contains breathing room — don't mix `p-4`/`p-6` in the same visual rhythm.
- **Typography.** UI text uses `font-sans` (Inter, default). Question/option/solution body text uses `font-serif` (Source Serif 4) — it's how teachers tell content apart from chrome. Both are loaded via `next/font` in `src/app/layout.tsx` and exposed as Tailwind utilities.
- **Color / brand (indigo, 2026-06-01).** The brand accent is **indigo** — chosen to unify with the `/notes` content palette. Three CSS vars in `globals.css`: `--brand` + `--brand-foreground` (fills — indigo-600 + white, AA-safe as a button bg in both themes) and `--brand-accent` (text/icon/border — indigo-600 light / indigo-400 dark, AA-legible as small text in both). `--ring` points at the brand so focus rings are branded. Tailwind exposes `bg-brand` / `text-brand-foreground` / `text-brand-accent` (+ a `brand` Button variant). **Application is SELECTIVE**: brand goes on chrome the eye lands on (primary CTAs, active nav, header mark, hero, stat numbers, table heatmap/peak-highlight, focus ring); near-black `--primary` stays the workhorse for secondary/admin buttons. **Off-limits:** the `/notes` + `/guide` *content* colors (concept-card indigo, amber traps, sky self-check, violet practice, emerald checkpoints) are content semantics — do NOT fold them into the brand token or recolor them. See [[brand-indigo-tokens]] + the 2026-06-01 Decisions-log entry.
- **Icons.** Use `lucide-react` for all icons. Never emoji or text glyphs (▾, ‹, ›) for UI affordances. Standard sizes: `h-3.5 w-3.5` for inline-with-text, `h-4 w-4` for buttons, `h-5 w-5` for the AppHeader logo.
- **Toasts.** `import { toast } from "sonner"`. Fire on every async user-initiated success or failure (save, upload commit, export download, sign-out). Setting an inline `error` state is fine, but never *replace* a toast with it — both should fire so the user can't miss the result while scrolled.
- **AppHeader.** Every page wraps its `<main>` in `<><AppHeader />…</>`. Don't re-add ad-hoc back-links, theme toggles, or sign-out buttons on individual pages — theme lives in the `ThemeToggle` island in the header (visible to anon + authed), sign-out lives in the UserMenu popover (authed only).
- **No Prisma.** Supabase RLS is the security boundary — every read/write goes through `@supabase/supabase-js` so the user's JWT carries through. Reach for `createSupabaseAdminClient()` (service-role) only in server-only contexts (seeds, cross-org admin) — it bypasses RLS by design.
- **Migrations are append-only.** New SQL goes in a new `000N_<name>.sql`. Apply via Supabase MCP `apply_migration`. Never edit a previously-applied file.
- **`.mcp.json` is gitignored.** Holds Supabase + Vercel personal access tokens. Don't commit.
- **Idempotent seeds + uploads.** `scripts/seed.ts` and the upload commit both check existence before insert; re-running is safe.
- **Content hashing for upload dedup.** `content_hash = sha256(normalised question text + sorted options + answer)` plus a unique index on **`(org_id, exam_id, content_hash)`** (migration 0038 — **per-exam**: was org-wide `(org_id, content_hash)` until 2026-06-15). Re-uploading the same file inserts 0 rows; the SAME question may recur across exams (CDS ↔ NDA share UPSC GAT English questions — org-wide dedup silently dropped the CDS copy). `commitStaged` upserts on `org_id,exam_id,content_hash`; `applyMockSync`'s content_hash lookups are exam-scoped to match.
- **Text normalization at write boundaries.** Long-form user-authored text (question, context, solution, options) goes through `normalizeNewlines` in the upload parser and the edit validator. The DB never carries literal `\n` (backslash+n) past the boundary; math zones are preserved verbatim. Any new write path that accepts long-form text must call the helper before insert/update — otherwise the render layer can't distinguish "real line break" from "literal text".
- **OMML + math defaults via post-processing.** Two `docx`-library limitations land on the same workaround. (1) `ImportedXmlComponent` wraps imported XML in an `<undefined>` element Word rejects, so we emit placeholder runs and swap them for OMML after `Packer.toBuffer`. (2) The library doesn't expose `<m:mathPr>` for settings.xml, and Word's built-in math defaults (`defJc=centerGroup`, `wrapIndent=1440`, non-zero margins) shift any paragraph containing a 2-D math element (`<m:f>` etc.) ~1″ right of plain-text paragraphs — option `(A) -3/4` ends up out of column with option `(A) -1`. `patchZip` in `src/lib/export/docxBuilder.ts` handles both: marker → OMML in `word/document.xml`, and `<m:mathPr defJc=left wrapIndent=0 lMargin=0 rMargin=0>` injected before `</w:settings>` in `word/settings.xml`.
- **Restart `npm run dev` after adding new routes.** Tailwind JIT can miss files created mid-session. Stop dev, `rm -rf .next`, restart before UI smoke tests.
- **`/notes` LaTeX in body prose only.** Four `SubtopicNote` / `ConceptUnit` fields render as plain text (no KaTeX) AND feed SEO `metadata.description` / JSON-LD where KaTeX would be invalid: `note.title`, `note.oneLineDefinition`, `note.whyItMatters`, `concept.name`. LaTeX in any of these leaks through as raw `\(\hat{i}\)` markup on the page AND in page metadata. **Keep math only in body fields** (`intuition`, `definition`, `formula.latex`, `authoredExample.{prompt,steps,answer}`, `trap.{title,body}`) — those go through `KatexRenderer` correctly. Use Unicode (`î`, `ĵ`, `k̂`, `Σ`, `°`) or plain prose for the four plain-text fields. **Body fields also support `**bold**`** (renders via KatexRenderer / RichText — use it for key terms), and the **`definition` field additionally supports `- ` bullet lists** (rendered by `RichText`): bullet *list-shaped* definitions (term/type/property enumerations), keep narrative ones as prose. The plain-text fields render `**`/`- ` literally — never use them there.
- **Word export: lowercase option labels at render only.** Bank stores `A/B/C/D` uppercase (Excel + DB convention); the `.docx` export renders them as `(a)/(b)/(c)/(d)` in both question paper and answer key (`opt.label.toLowerCase()` in docxBuilder). Browse cards + edit form still show uppercase — only the rendered Word doc is lowercased. If a future surface needs to render bank-style labels, follow the same boundary: lowercase at render, never in the DB.
- **Word export: underline bypasses the math pipeline.** DB convention is `\(\underline{\text{word}}\)` (or `\(\underline{\textit{word}}\)` for italic+underline — biology taxonomy questions). KaTeX renders these in the browser; the docx export detects them via `UNDERLINE_BYPASS_RE` in [src/lib/export/ommlBuilder.ts](src/lib/export/ommlBuilder.ts) and emits a native Word run (`TextRun({ text, underline: { type: "single" }, italics? })`) instead of routing through `temml → mml2omml → <m:borderBox>` — Word doesn't reliably draw the bottom border on inline-math borderBox under our injected math defaults. Trailing punctuation INSIDE the delimiters (`\(\underline{\text{x}}.\)`) is split off into a separate text segment. Any pattern outside the regex (bare `\underline{word}`, chained `\text{}\text{}`, `\textbf` variants, block math) falls through to the OMML pipeline and renders without an underline in Word — run `npm run audit:underlines` after each new English / Biology batch to catch fall-throughs.
- **Tables in question content use GFM pipe-tables (2026-06-02).** A table inside a question `text` or `context` is authored as a standard Github-flavored markdown pipe-table — a header row **plus a `|---|---|` separator row**, then data rows. The separator row is mandatory and is what distinguishes a real table from inline `|·|` math (determinant `\(|A|\)`, abs value `|x|`, cell notation `Zn|Zn²⁺`): a line of pipes with **no** following separator stays prose. `parseTableBlocks` in [src/components/math/parseTableBlocks.ts](src/components/math/parseTableBlocks.ts) (pure, math-masked via `maskMathZones`, TDD in `tests/parse-table-blocks.test.ts`) splits text into prose + table blocks; cells keep their `\(...\)` math and `**bold**`. Rendered by `BlockText` (`src/components/math/BlockText.tsx`) on `/browse` (expanded card only — collapsed preview stays plain `KatexRenderer` so a table can't blow past `line-clamp-2`) + the editor Preview + the `/notes` mastery-check / `/guide` worked-example cards (`WorkedExampleCard`'s `example.context` + `example.text`, 2026-06-04), and as a native Word `<w:tbl>` in `docxBuilder` (the question NUMBER rides on the first paragraph; a stem opening with a table gets a numbered empty paragraph first). **No DB primitive** — it's all in the existing `text`/`context` columns; `normalizeNewlines` is compatible (it upgrades an Excel-authored literal-`\n` table into real newlines). **Future-only**: the existing 13 Statistics (lossless 2-row linearization) + 37 Match-Lists were NOT backfilled — they still render as linearized text. Options don't support tables (v1). For a genuine ≥3-column data grid that can't be a markdown table, fall back to a question image like a diagram. **Any surface rendering a long-form field that MAY contain a pipe-table (a solution/model-answer, not just stem/context) must render via `BlockText`, not `KatexRenderer`** — `KatexRenderer` prints a table as raw `| p | q |` text. The `/board` + `/browse` solution reveals both shipped on `KatexRenderer` and rendered truth-table answers as raw pipes (fixed 2026-07-06); `BlockText` fast-paths to `KatexRenderer` when there's no table, so it's a safe drop-in.

## Recurring pitfalls

Patterns that have bitten this codebase more than once. Each one earned its place by causing a real production regression — read before writing new code that resembles the shape.

- **PostgREST 1000-row cap on raw `.select()`.** Any `client.from(...).select(...)` that derives a count, a distinct set, a sort, or any aggregate from the *row payload* (rather than response headers via `count: "exact"` or a SQL aggregate via RPC) is suspect once the table can exceed 1000 rows. PostgREST silently truncates at row 1000 — no error, just wrong answers. **Already bit us three times:** dashboard totalQuestions (migration `0018` get_dashboard_stats), PYQ-year filter dropping older years (migration `0019` get_pyq_years), and upload commit dedup races (fixed by switching to `.upsert(..., { onConflict, ignoreDuplicates: true })` — let the DB unique index enforce dedup, not an in-memory `Set`). **Audit checklist before writing any new `.select()`:** (1) Is the row payload itself the answer, or are you computing something from it? (2) If computing, can the underlying table exceed 1000 rows ever (today or as the bank grows)? (3) If yes, use `count: "exact", head: true` for counts, or write a `security invoker` RPC that does the aggregate in Postgres. Never trust a row-derived count from `.select()` past the first 1000 rows. **Bit us twice more 2026-06-11:** `quiz:lint` used a bare `.limit(2000)` which PostgREST still caps at 1000, so it silently scanned only 1000 of ~1762 ready atoms (fixed by paging in 1000-row `.range()` windows); and **the sibling self-imposed-limit trap** — `/dashboard/quizzes` `listAssembledQuizzes` had a hard `.limit(60)` and a "Quizzes built" stat derived from `list.length`, so once the table crossed 60 quizzes (now 109) the oldest silently vanished from the filtered admin view AND the stat under-reported. Rule: a hard `.limit(N)` on a list hides rows once the table exceeds N, and any stat from `list.length` lies — derive counts from a true `count:"exact"`, and raise/paginate the list.
- **`next dev` is more forgiving than `next start` for server↔client prop serialization.** Functions and other non-serializable values passed from a Server Component to a Client Component compile cleanly under `next dev` but throw at SSR time under `next start` ("Functions cannot be passed directly to Client Components"). This bit us on the 2026-05-13 Pagination revert. **Mitigation:** the pre-push hook in `.githooks/pre-push` runs `next build` before allowing a push, so this class of bug is caught locally rather than after a Vercel deploy. Don't `git push --no-verify` unless you know exactly why.
- **`next build` does NOT exercise a DYNAMIC (`ƒ`) page's render — so the build gate is blind to its render-time throws.** Only static/SSG (`○`/`●`) routes are prerendered at build; a server-rendered-on-demand page (any page that awaits cookies / a per-request query — most `/guide/*` + `/notes/*` pages that call `resolveTaxonomy` via the anon client) is never executed until a real request, so a render exception passes `typecheck` + `lint` + `next build` + the full pre-push gate and only 500s in production. **Bit us 2026-06-14:** the new `/guide/nda-physics/ncert-map` page named a `<NcertChip>` prop `ref` — React **reserves** `ref` (it's never passed to a plain function component, so the value was `undefined` at render → "Refs cannot be used in Server Components"). Typecheck passed because the prop was explicitly typed `{ ref: NcertRef }`; the build passed because the page is `ƒ`. **Three mitigations:** (1) never name a component prop `ref` (or `key`) — they're React-reserved regardless of your prop type; (2) **curl/browser smoke-test every new DYNAMIC route before claiming done** — the build gate's green is necessary but NOT sufficient for `ƒ` pages (it IS sufficient for `○`/`●` pages, which prerender). A data-only test (like the ncert-map taxonomy test) doesn't render the page, so it can't catch this either. (3) **Confirm the smoke test actually REACHED the page** — an anon curl to any route under the `src/middleware.ts` matcher (`/dashboard/*`, `/account/*`, `/upload*`, `/uploads*`) is bounced by **middleware** before the page compiles, so the 307 tells you nothing about your code. Check the dev log for a `○ Compiling /your/route` line; no line = the request never got there. Bit us 2026-07-15 (the paper-editor rebuild — a "clean" 307 was pure middleware). For an auth-gated `ƒ` page there is **no headless proof of render** (the repo has no jsdom/testing-library/Playwright): say so plainly and hand the browser check to the user rather than implying the route was verified. See [[probe-must-reach-the-code]].
- **Source-source subtopic name collisions during bulk chapter merges.** When canonicalizing N source chapters into one target chapter, a bulk `UPDATE subtopics SET chapter_id = '<tgt>' WHERE chapter_id IN ('<src1>', '<src2>', ...)` can fail with `23505` on `subtopics_chapter_id_name_key` even if a pre-flight source-vs-target collision check came back clean — because two sources may share a same-named subtopic that collides only once both are reparented. Bit us on the NDA Physics E&M cluster (5 sources → "Magnetic Field Inside a Solenoid" appeared in two of them). **Mitigation:** process sources sequentially via a `DO $$ FOR mapping IN (VALUES (...)) LOOP ... END $$` block; each iteration redirects colliding questions, deletes colliding source subtopics, reparents the rest, updates remaining question chapter_ids, and deletes the source chapter — so by the time source 2 merges, source 1's content is already in target and the standard collision-handling kicks in. Pattern + full template in `[[reclassification-sql-pattern]]`.
- **Catch-all chapters and subtopics drift until you reclassify per-question.** Buckets named "Mechanics", "Physics", "Error Identification in Sentences" collect every question that doesn't cleanly fit a more-specific name. They look harmless during a chapter-level merge but rot the bank's usefulness for technique drills. **Mitigation:** when a chapter or subtopic holds ≤~50 mixed-topic questions, read each stem and produce a `(question_id, target_canonical_id)` mapping; execute as a `DO $$ FOR m IN (VALUES (qid, tgt)) LOOP ... END $$` that (a) looks up the question's source subtopic, (b) finds same-named subtopic in target chapter, (c) redirects+deletes on collision, otherwise reparents+moves chapter_id. Precedents: Spotting Errors 29 q (2026-05-15 NDA English); Mechanics 19 q + Physics 26 q catch-all chapters (2026-05-15 NDA Physics). Beyond ~50 q the user prefers chapter-level merge + subtopic-cleanup as a follow-up pass.
- **`/notes` subtopic slugs are GLOBALLY unique, not chapter-scoped.** `question_concept_tags` keys on `(question_id, subtopic_slug, concept_slug)` with **no chapter or subject column**, and `loadConceptDrills` / the mastery-checkpoint query filter by `subtopic_slug` ALONE. So two chapters that both use a slug like `foundations` will cross-contaminate each other's drill lists + checkpoints. Bit us 2026-05-30: MHT-CET Indefinite Integration reused Sound's `foundations` slug — notes-lint caught it as "DB tag has unknown concept_slug" because the other chapter's concepts don't match. **Mitigation:** every notes subtopic slug must be unique across ALL chapters in `NOTES_CHAPTERS` (the URL segment can repeat per subject route, but the slug used as the concept-tag key cannot). MHT-CET's foundation subtopic was renamed `foundations` → `fundamentals`. notes-lint surfaces the collision but only *after* tags are inserted — pick distinctive slugs up front.
- **Renaming a SHIPPED chapter silently rots its `/guide` + `/notes` cross-refs.** The DB taxonomy and the guide/notes editorial TS are joined only by NAME at request time (`resolveTaxonomy`), so a Phase-D rename/merge leaves the TS pointing at a dead subtopic — the "Drill the N →" CTA resolves to an EMPTY `/browse` filter, no error. Bit us twice on 2026-05-30: the Sound notes 5→4 redesign broke the `/guide/nda-physics` Sound playbook + strategy `mustDrill` + CHAPTER_TABLE prose; the 2026-05-29 Probability merge ("Probability with Dice" → "Probability via Counting") broke two `nda-maths` principle drills + the Probability tier. **Mitigation:** after any rename/merge of a shipped chapter, sync `/guide` `_data` (playbooks `subtopics[]`, strategy `mustDrill`/`skipSubtopics`, principles `drill`, compounds filters, prose counts) + `/notes` `_data` + concept tags, then run `npm test` — the 7 playbook guides + CA themes + Maths each have a `describe.skipIf(!HAS_ENV)` live-taxonomy resolution test (`guide-nda-<subject>-playbooks.test.ts`; `guide-nda-maths-taxonomy.test.ts` for Template A) that fails on drill-target drift. Full procedure: [[shipped-chapter-rename-downstream-sync]]. The `/browse` backlink chip (`getQuestionResources` name lookup) + the single-page Economics chapter CTA are the cross-link surfaces still untested.
- **Integration-test fixtures leak into the LIVE bank when `afterAll` is interrupted — and only `org_id` reliably catches them.** Every DB-integration test inserts throwaway rows (org, questions, taxonomy) into the single prod Supabase project and cleans them in `afterAll`; a parallel/killed/throwing run skips that cleanup, stranding PUBLIC fixtures on `/browse` and inflating the bank counts. Bit us 2026-06-11: 18 fixture questions (11 PUBLIC) + 12 orgs leaked. **No content signal is complete** — `source_file`+`upload_job_id` both NULL misses fixtures that set a test `upload_job_id`; text-pattern misses the `goodXlsxBuffer` upload-flow fixtures (realistic stems, **real sha256 `content_hash`, under canonical taxonomy**); `content_hash !~ '^[0-9a-f]{64}$'` (0 real rows) misses those same ones. **The one universal signal is `org_id`:** every fixture belongs to a throwaway org whose name carries an 8-hex run-id (`randomUUID().slice(0,8)`). **Mitigation:** `global-teardown` is now an org-keyed cascade sweep (`isTestOrgName`, [[test-data-leak-org-signal]]) — but it's a SAFETY NET that only runs at the end of a full `vitest run`. A subset/watch run that creates fixtures and is then killed leaves them until the next full suite. After any interrupted DB-test run, sweep manually or run a full `npm test`. To clean: clear `question_reports` (its `org_id` FK is RESTRICT) then delete the test orgs (CASCADEs questions→options/tags/reports + org_members + upload_jobs).

## Design axes

Load-bearing design distinctions for the project. Each one earns its place by being structural — getting the axis wrong has cost real work, and the answer to "which axis does this live on?" is non-obvious for the named feature areas.

### Tag taxonomies — principles (horizontal) vs concepts (vertical)

**`/guide` principles** and **`/notes` concepts** are different kinds of tag and must NEVER share a schema or be merged into one taxonomy.

| | Principles | Concepts |
|---|---|---|
| Axis | Horizontal — cross-subtopic | Vertical — within-subtopic |
| Cardinality | ~20 in NDA Maths | ~5–10 per subtopic × hundreds = thousands at scale |
| Storage | TS modules (`/guide/.../principles.ts`) + curated `extraQuestionIds` | DB table `question_concept_tags` (migration 0021) |
| Authoring | Editorial — hand-curated, slow update cadence | Per-upload — admin tagging UI or chat session, fast cadence |
| Value comes from | **Selectivity** (only the top-20, hand-picked) | **Coverage** (every relevant question tagged) |
| Identity question | "What unifying lens does this question demand?" | "What specific technique within this chapter?" |

**The wall — non-negotiable:**
- DON'T migrate `/guide` principles to a DB table. Hand-curation is the signal-to-noise mechanism; "scaling" them dilutes their value.
- DON'T bundle principles into `question_concept_tags` via a `tag_kind` discriminator. Flattens the strategic distinction.
- DO share infrastructure at the seam: one admin tagging UI on `/questions/[id]/edit`, one notes-lint validator, future LLM-suggest can suggest both kinds. Sharing UI ≠ sharing schema.

**Why this earned a section:** The initial concept-tags proposal (Phase 1, 2026-05-17) was a unified `question_tags` table. User pushed back; I conceded. Both axes shipped separately (principles still in TS, concepts in migration 0021) and the wall has held. This section exists so future tag-related features (admin UI, LLM-suggest, AI tutor grounding, MHT_CET_AI integration) don't re-litigate it from scratch.

### Cross-link backlinks — chapter-level (automatic name lookup) vs tag-level (manual DB-tagged override)

The `/browse` QuestionCard chip row (Tier 1 + Tier 1.5, 2026-05-18) renders **two distinct classes of backlink** and the wall between them matters. Same dropdown of chips, two completely different authoring loops and data sources.

| | Chapter-level chips | Tag-level chips |
|---|---|---|
| Examples | "Playbook: Sound" · "Concept notes" | "Lever: Vieta" · "Concept: Weighted Mean" |
| Source | Name-based lookup at render time | DB row in `question_principle_tags` / `question_concept_tags` |
| Authoring cost | **Zero per question** — purely a function of `(exam, subject, chapter, subtopic)` | **Manual per question** — chat tagging session, INSERT with `ON CONFLICT DO NOTHING` |
| Coverage | 100% of questions whose chapter has a guide / subtopic has notes | Only questions explicitly tagged (today: 488 principle tags · 262 concept tags) |
| Failure mode | Silent break when DB chapter renamed (no lint catch yet — see ROADMAP "notes-lint guide-side rename validation") | Silent fallback to generic chip when slug doesn't resolve via `getPrincipleName` / `getConceptName` |
| Override behaviour | The default; renders for all qualifying questions | When present, **replaces** the chapter-level chip for the same axis (more specific wins) |
| Resolver | `getQuestionResources({exam, subject, chapter, subtopic})` in `src/lib/links/questionResources.ts` | `getQuestionResources({...}, tags)` — same function, second arg from `getResourceTagsForQuestions` batch |

**The wall — design intent:**
- DON'T expand the chapter-level lookup to do "fuzzy" matching when a chapter rename happens. The failure mode (chip disappears) is the correct signal — fix the rename, don't paper over the drift.
- DON'T attempt to back-fill tag-level chips from the chapter-level data (e.g. auto-create a `Lever: <chapter-name>` chip when no principle tag exists). That destroys the curated-vs-automatic distinction and floods low-leverage questions with meaningless tag chips.
- DO let tag-level chips quietly fall through to chapter-level chips when the tag's slug doesn't resolve. Better a generic "NDA Maths strategy" chip than a broken `/principles/<unknown-slug>` link.
- DO share infrastructure at the seam: both axes flow through the same `getQuestionResources(input, tags?)` function, both render via the same `<ResourceChip>` component in QuestionCard. The two-tier system is a function-signature distinction (optional second arg) not two separate code paths.

**Why this earned a section:** The 2026-05-18 Tier 1.5 ship added tag-level overrides AFTER the Tier 1 chapter-level chips were in production. The temptation in the moment was to refactor into "one unified backlink table" or to have tag-level chips deduplicate against chapter-level chips. Both ideas are wrong — they conflate two different authoring loops (curated tagging session vs no-touch render-time mapping) and two different coverage shapes (long-tail per-question vs blanket-per-chapter). The split shipped cleanly because the function signature preserved the asymmetry: `tags?` is optional, the resolver short-circuits chapter-level chips when a more-specific tag-chip exists, and untagged questions still get the generic chip — graceful fallback throughout. Sister wall to the tag-taxonomies axis above.

### Guide strand axis — execution-mode (chapter-partitioning) vs tier-style (chapter-tiering)

Within Template B variants, the **strand split** is the strategic axis the strategy page renders against. There are two fundamentally different ways to construct it, and they are NOT interchangeable — picking the wrong one produces a strategy axis that sorts questions by nothing meaningful.

| | Execution-mode strands | Tier-style strands |
|---|---|---|
| Subjects | NDA English (R/Rule/Reason), NDA Chemistry (R/Rule/Calculate), NDA Biology (R/Apply/Verify), NDA Geography (R/Apply/Verify) | NDA History (Cornerstone/Foundation Recall/Quick-Win) |
| Strand semantics | Each strand is a SKILL bucket (recall a fact / apply a rule / trace a mechanism / evaluate a statement). Chapters get grouped into a strand by their dominant execution mode. | Each strand is a STRATEGIC TIER (cornerstone weight / foundation recall / quick-win). Chapters get grouped into a strand by their bank share + %HARD profile. |
| Recall slot | Stable — there's always a Recall strand (named-fact recall is universal in Indian entrance exams). | Stable in spirit (Foundation Recall) but the slot SEMANTICS bent — it now groups chapters by tier, not by execution mode. |
| When to pick | Execution modes PARTITION chapters: one cluster of chapters is 60%+ dominated by one mode, others are 20%- on that mode. | Execution modes are UNIFORM across all chapters (25–45% everywhere) — can't partition. AND/OR one chapter has dominant bank share (40%+) that warrants its own Cornerstone tier. |
| Decision probe | For each candidate mode (recall/rule/apply/verify/calculate/reason/multi-statement/date-anchored), count `q × chapter_spread` AND per-chapter %. Top mode at 60%+ in one cluster = execution-mode strands work. | Top mode is 25–45% of every chapter = uniform = falls back to tier-style. Use bank-share + %HARD per chapter as the partition signal instead. |
| HARD calibration | Strand-level (densest-HARD strand called out — Geography's Apply at 23% avg HARD). | Implicit in the tier-structure — Cornerstone IS the densest-HARD tier by construction (History's Cornerstone = Modern India 34% HARD). |

**The wall — design intent:**
- DON'T force execution-mode strands when modes don't partition. History's multi-statement (70 q × 4 ch · 43% HARD) and date-anchored (61 q × 4 ch · 43% HARD) cut UNIFORMLY across chapters — a Bio/Geo-style R/Apply/Verify split would force lopsided cuts (Recall 44 q : Date 163 q : Verify 53 q if grouped by chapter's dominant mode). The strategy axis would sort by nothing meaningful.
- DON'T force tier-style strands when execution modes DO partition cleanly. English's Vocab/Idioms (Recall) and RC/Cloze (Reason) chapters are genuinely different SKILL types, not just different priorities — a Cornerstone/Foundation/Quick-Win split would lose that information.
- DO let the decision probe pick. Test execution-mode first (Template B default); fall back to tier-style only when modes are uniform.
- DO share infrastructure at the seam: both axes use the same `STRATEGY_STRANDS` data shape (each strand has `id`, `label`, `pitch`, `approach`, `chapters: StrandChapter[]`) and the same strategy-page renderer. The two-axis distinction is in the BUCKET MEANINGS (`PlaybookBucket = "recall" | "apply" | "verify"` for Bio/Geo vs `"cornerstone" | "foundation" | "quickwin"` for History) — same code path, different semantics.

**Why this earned a section:** The 2026-05-19 NDA History ship was the first time Template B's strand axis itself bent. Before History, every Template B variant had bent the second + third SLOTS within an execution-mode axis (Rule→Apply for Bio, Calculate→Verify for Chem) — but the axis itself was always execution-mode. History exposed the next level: when execution modes don't partition chapters at all, the axis itself has to change. The temptation in the moment was to force one of the existing slot-bend patterns onto History (most naturally R/Apply/Verify like Bio + Geo) — that would have shipped a strategy page where students see "Apply chapters" and "Verify chapters" labels but no chapter actually leans either way, sorting by nothing. The tier-style fallback shipped cleanly because the strand data shape was already general (chapters grouped under labelled strands with a pitch + approach) — only the bucket vocabulary changed. Sister wall to the tag-taxonomies + cross-link-backlinks axes above: in all three, the right call is to preserve an asymmetric distinction at the shared seam rather than to flatten for elegance.


### Content-organisation axis — book-structure (`section_*`, /board) vs conceptual (`subtopic`, /browse + /notes)

A board-textbook chapter is stored ONCE but organised on **two orthogonal axes**, and they must not be conflated:
- **Conceptual — `subtopic`** (`chapters`→`subtopics`, `order_index`): technique/topic grouping ("Combined Equation", "Angle Between Lines"). Drives `/browse` filters + `/notes` teaching order. A single book Exercise's questions are deliberately spread across several subtopics by concept.
- **Book-structure — `section_kind`/`section_group`/`section_label`/`section_seq`** (migration 0043): the book's physical layout (§2.1 Solved Examples → Exercise 2.1 → … → Miscellaneous), in reading order. Drives `/board` ONLY.

**The wall:** the `/board` reader groups by `section_group` (book section), NOT by `subtopic` — grouping by subtopic would shatter a single contiguous book Exercise into pieces under different headers. Conversely `/browse`+`/notes` never use `section_*`. The two axes are joined only by living on the same `questions` row. **Why it earned a spot:** the reader was first designed to group by `subtopic.order_index`; Matrices exposed that Exercise 2.2 (Q.1–6) splits across three subtopics, so the book axis had to be a separate, PDF-verified `section_*` outline (`scripts/stateboard/sections.ts`). Book order is NOT derivable from `subtopic` NOR reliably from the messy `question_number` string — it's authored per chapter and gated by `board:lint`. See [[board-reader]].

## Guide structure templates

## Engagement engine — principles gate (always-on)

The engagement engine ties PYQ Vault's scattered behaviour signals into a loop that improves learning + retention. **This gate is non-negotiable — like the "no slop" rule, every engagement mechanic must clear it before it ships.** Imported + adapted from the sibling English AI Tutor's hard-won engine (`Downloads/English_AI_Tutor`), whose findings we inherit rather than re-learn.

**Every mechanic must serve ≥1 learning principle** — else it's a dark pattern, not a feature:
- **Retrieval practice** — test recall, don't re-expose. **Spaced repetition** — resurface what the student got wrong until mastered (80%). **Immediate feedback** — results on the same/next screen, never a dashboard they must go find. **Deliberate practice** — drill the *specific* thing they missed, not "keep practising". **Mastery before progression** — gate on demonstrated 80%, don't reward accumulated low scores. **Metacognition** — every metric we track is shown to the student in plain language (trends, weak chapters, days-to-exam). **Growth-framed feedback** — name what went well + what's next, never a bare score.

**Forbidden (dark patterns — this is a stressed-teen exam-prep cohort):** leaderboards (demotivate the bottom half in a known-peer setting), hearts/lives (anxiety), variable rewards/loot boxes (exploitative), streak freezes/shields (complexity, no learning value), and **vanity milestones** ("logged in 3 days", "earned 100 XP" — awards must be genuine learning achievements).

**Two structural rules the AI Tutor learned the expensive way:**
1. **Measure the usage shape BEFORE building a mechanic.** They shipped 6 milestone kinds; 3 fired *zero* times because students study in **bursts, not daily** — daily streaks are silent demotivation for this cohort. For an exam app, **prefer deadline/goal-progress over daily streaks.** Read `user_activity` first; pick mechanics that fit the real data.
2. **Awards are server-side + idempotent** (dedupe_key), and **celebrations fire at the trigger surface** (the mock-result page), never a buried dashboard.

**The spine (built 2026-07-12):** `user_activity` (migration 0052) is the append-only event log every mechanic reads from — pure core `src/lib/activity/events.ts`, best-effort writer `src/lib/activity/service.ts` (never blocks the primary action), emitters on mock-submit / notes-mastery+checkpoint / bookmark, backfill `scripts/activity/backfill.ts`. **Signed-in only** for now (anon top-of-funnel stays SEO-clean). See [[project-engagement-engine]] + the Decisions entry below.

## Decisions log

Why behind architectural pivots — saves future-you from "why didn't we just…?".

**Convention:** topical intros (like "Foundations" below) sit at the top. Dated entries are bucketed by month — `### YYYY-MM` per month. When a new month begins, add a new `### YYYY-MM` sub-section above the prior one. **Within a month, entries are ordered newest-first (reverse chronological top-down): a new entry goes at the TOP of its month's block.** Net result: the most recent entry anywhere in the log is the first dated entry a reader sees after the foundations. This lets a reader collapse historical months mentally and focus on what's recent.

### Foundations (M1–M3, 2026-05-08)

The load-bearing choices made during the initial scaffold. Every later phase rests on these — re-litigate only with explicit reason.

- **No Prisma.** Supabase RLS is the security boundary; Prisma uses a single privileged DB user and bypasses RLS by default. Forcing per-request `SET LOCAL` JWT injection fights the tide. `@supabase/supabase-js` carries the user's JWT through naturally.
- **RLS helpers in `private` schema.** PostgREST exposes any `public.*` function as a `/rest/v1/rpc/<name>` endpoint. Supabase advisor flagged `current_user_org_id()` / `current_user_is_admin()` as callable by `anon` and `authenticated`. Functionally safe (returns `null`/`false` for anon) but defence-in-depth — moved to a schema PostgREST doesn't expose.
- **OMML via marker-and-post-process.** The `docx` library's `ImportedXmlComponent.fromXmlString` wraps imported XML in an `<undefined>` element that Word refuses to open. We render placeholder text where math should go, then patch `word/document.xml` after `Packer.toBuffer`. Sidesteps the library quirk; works for arbitrary OMML.
- **Word export = ZIP of two files.** First version was a single .docx with a 3-way layout toggle. User asked to split: a Question Paper distributable without leaking answers, and a separate Answer Key. One ZIP keeps the bundle obvious. **Superseded 2026-05-13** — ZIP killed for mobile UX; route now returns one .docx per request via a required `kind` selector.
- **Hard 200/export cap, no auto-split.** Vercel function timeout is the binding constraint. A clear error ("narrow filters") ships faster than a zip-of-zips. Revisit if a teacher genuinely needs 500 questions in one paper.
- **Chapters/subtopics auto-create, subjects don't.** Subjects are top-level taxonomy curated centrally; auto-creating "Phyiscs" from a typo would corrupt the canonical list. Chapters/subtopics are per-upload working data — small typo cost, and a merge tool can clean up later.

## After a new upload

When a new question-batch lands, run the 6-step ritual in order. The upload pipeline is auto (taxonomy auto-creates, `content_hash` dedup, default PUBLIC visibility, live counts in `/browse` + dashboard + `/guide` TOP_11 + `/notes` drills). What's NOT auto and needs this ritual: **tag coverage, taxonomy fragmentation cleanup, and TS-static editorial copy**.

1. **Sanity-check the batch** (always) — confirm `inserted` vs PUBLIC/PRIVATE counts, PYQ metadata stamped, no missing years
2. **Taxonomy delta cleanup** (if ≥5 new subtopic auto-creates or a new chapter name) — Phase D delta inline; don't restart from scratch. Precedent: 2026-05-17 NDA Maths re-Phase-D (~770 new auto-creates closed in one session)
3. **Principle-tag delta survey** (if new questions in TOP_11 chapter footprints) — incremental per-new-chapter, not whole-bank
4. **Concept-tag delta session** (if new questions in `/notes`-covered subtopics) — also revisit dropped-gap ConceptUnits; bank growth can mature what was previously dropped
4b. **Notes-coverage check** (if new questions in a `/notes`-covered chapter) — `npm run notes:coverage <subjectRoute> <chapterSlug>` and triage the macro/technique channel. New uploads are how a *technique gap* drifts in (a fresh question using a method the notes don't teach); this is the routine catch for it. Add a concept for any real gap.
5. **Editorial copy refresh** (if counts move ≥5–10%) — `whyItMatters`, OVERVIEW constants, CHAPTER_TABLE, strategy %HARD, trends callouts. Mechanical TS edits
6. **Integrity check** (always) — `npm run notes:lint` + `npm run prepush` before commit

Steps 2–5 (incl. 4b) are conditional and can be deferred / queued across sessions. Full procedure + SQL probes + skip-conditions: [[post-upload-ritual]].
