# Question Bank — project notes

Free, public past-year-question paper builder for Indian entrance exams. Anyone can filter the public bank by exam/chapter/subtopic/difficulty/PYQ year, then download a Question Paper + Answer Key as Word files. Admins (org members) upload Excel batches privately, then flip individual questions PUBLIC. Sibling app `MHT_CET_AI` posts finalized mocks to `/api/sync/mock` for cross-app dedup. Currently MHT-CET + NDA; IPMAT, CUET, NEET, JEE Main on the roadmap.

## Multi-tenancy + visibility model

Per-school orgs, RLS-enforced. Three tiers of access:
- **Service role** (seed scripts, server-only admin actions, `/api/admin/members`) bypasses RLS by design — never expose to client code.
- **ADMIN** can do everything in own org: insert + update + delete questions, write options, upload Excel batches, auto-create chapters/subtopics, flip visibility, triage reports, manage members.
- **TEACHER** (as of migration 0025 / 2026-05-26) can **edit** question content — text, options, taxonomy moves, difficulty, PYQ metadata, images, concept/principle tags, leave-set — in own org. Cannot upload Excel, delete questions, flip PUBLIC/PRIVATE, auto-create chapters/subtopics, triage reports, or manage members. Server-side guard in `applyEdit` rejects `payload.visibility` changes from TEACHER (`kind: "forbidden_field"` → HTTP 403) so a tampered request can't bypass the hidden UI toggle.
- **anon** (no JWT) can read PUBLIC questions/options + all taxonomy. Cannot write anything.
- **STUDENT** (signed-in, self-serve, **no `org_members` row** — added 2026-06-01) registers at `/signup` (Google OAuth or email/password). By RLS construction they get zero private data; what an account unlocks is in-app question reports today + premium content via the entitlement axis below. Org-less = student (admins always get an `org_members` row atomically), so `/dashboard` redirects them to `/browse`.

**Premium entitlement axis (orthogonal to orgs, migration 0026).** Paid/comped access lives in `public.entitlements`, keyed on `auth.users(id)` — NOT org-scoped, because a student has no org. A grant unlocks a `scope` ('all' = full premium); `source` ∈ `razorpay | comp | manual` (the gate is **source-agnostic** — `userHasAccess` just asks "active entitlement for this scope?"; staff/org-members bypass the paywall). Writes are **service-role only** (no write RLS); reads are own-row only. Consumers: the `/notes` preview-gate (`tier:"paid"` chapters), `/pricing`/`/account`, the Razorpay webhook, and the `/dashboard/entitlements` comp UI. See the 2026-06-01 Decisions log entry + [[project-paywall-build]].

Each question has a `visibility` enum (`PUBLIC | PRIVATE`, default **PUBLIC** as of migration 0022 / 2026-05-17 — was PRIVATE prior). Read RLS is the union of two permissive policies: `(visibility = 'PUBLIC')` for everyone, plus `(org_id = private.current_user_org_id())` for authenticated org members on their own org's PRIVATE rows. Authenticated users see PUBLIC across all orgs + their own PRIVATE; anon sees only PUBLIC. Admins flip per-question visibility from the edit page.

RLS helpers live in the **`private` schema** (not exposed by PostgREST): `private.current_user_org_id()`, `private.current_user_is_admin()`, `private.current_user_can_edit_questions()`. New org-scoped policies should reference these. Use `current_user_is_admin()` for destructive / privileged ops (DELETE, upload, visibility flip, reports triage, member management); use `current_user_can_edit_questions()` for content edits that TEACHER should be allowed to do.

Cost: ~3–4 min (full suite + build). Activated by the `prepare` script (`git config core.hooksPath .githooks`) on `npm install`. `.gitattributes` pins LF on `.githooks/*` so the shebang resolves on Linux/WSL contributors. Escape hatch for WIP pushes: `git push --no-verify` — don't reach for it unless you know why.

> **CI gate.** `.github/workflows/ci.yml` runs the **full** gate (typecheck → lint → `notes:lint` → `notes:latex` → `npm test` → build) on every push to `main` + every PR. The local pre-push hook now runs this same chain (see Pre-push gate above), so CI is a backstop rather than the first place these checks run — it still matters because it runs on a clean checkout with repo secrets even if someone `--no-verify`s. Requires three repo secrets (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`); without them the build + DB steps fail and the DB tests skip. Runs against the single prod Supabase project (test rows auto-swept by `global-teardown`) — point the secrets at a staging project if write traffic gets noisy. Vercel still owns deploys; CI is the correctness gate.

## Conventions specific to this project

- **Spacing scale.** Page wrappers `p-8`, content cards (CardContent default) `p-6`, compact cards (FilterBar etc.) `p-4`, nested option blocks `p-3`. Pick the smallest tier that contains breathing room — don't mix `p-4`/`p-6` in the same visual rhythm.
- **Typography.** UI text uses `font-sans` (Inter, default). Question/option/solution body text uses `font-serif` (Source Serif 4) — it's how teachers tell content apart from chrome. Both are loaded via `next/font` in `src/app/layout.tsx` and exposed as Tailwind utilities.
- **Color / brand (indigo, 2026-06-01).** The brand accent is **indigo** — chosen to unify with the `/notes` content palette. Three CSS vars in `globals.css`: `--brand` + `--brand-foreground` (fills — indigo-600 + white, AA-safe as a button bg in both themes) and `--brand-accent` (text/icon/border — indigo-600 light / indigo-400 dark, AA-legible as small text in both). `--ring` points at the brand so focus rings are branded. Tailwind exposes `bg-brand` / `text-brand-foreground` / `text-brand-accent` (+ a `brand` Button variant). **Application is SELECTIVE**: brand goes on chrome the eye lands on (primary CTAs, active nav, header mark, hero, stat numbers, table heatmap/peak-highlight, focus ring); near-black `--primary` stays the workhorse for secondary/admin buttons. **Off-limits:** the `/notes` + `/guide` *content* colors (concept-card indigo, amber traps, sky self-check, violet practice, emerald checkpoints) are content semantics — do NOT fold them into the brand token or recolor them. See [[brand-indigo-tokens]] + the 2026-06-01 Decisions-log entry.
- **Icons.** Use `lucide-react` for all icons. Never emoji or text glyphs (▾, ‹, ›) for UI affordances. Standard sizes: `h-3.5 w-3.5` for inline-with-text, `h-4 w-4` for buttons, `h-5 w-5` for the AppHeader logo.
- **Toasts.** `import { toast } from "sonner"`. Fire on every async user-initiated success or failure (save, upload commit, export download, sign-out). Setting an inline `error` state is fine, but never *replace* a toast with it — both should fire so the user can't miss the result while scrolled.
- **AppHeader.** Every page wraps its `<main>` in `<><AppHeader />…</>`. Don't re-add ad-hoc back-links, theme toggles, or sign-out buttons on individual pages — theme lives in the `ThemeToggle` island in the header (visible to anon + authed), sign-out lives in the UserMenu popover (authed only).
- **No Prisma.** Supabase RLS is the security boundary — every read/write goes through `@supabase/supabase-js` so the user's JWT carries through. Reach for `createSupabaseAdminClient()` (service-role) only in server-only contexts (seeds, cross-org admin) — it bypasses RLS by design.
- **Migrations are append-only.** New SQL goes in a new `000N_<name>.sql`. Apply via Supabase MCP `apply_migration`. Never edit a previously-applied file.
- **`.mcp.json` is gitignored.** Holds Supabase + Vercel personal access tokens. Don't commit.
- **Idempotent seeds + uploads.** `scripts/seed.ts` and the upload commit both check existence before insert; re-running is safe.
- **Content hashing for upload dedup.** `content_hash = sha256(normalised question text + sorted options + answer)` plus a unique index on `(org_id, content_hash)`. Re-uploading the same file inserts 0 rows.
- **Text normalization at write boundaries.** Long-form user-authored text (question, context, solution, options) goes through `normalizeNewlines` in the upload parser and the edit validator. The DB never carries literal `\n` (backslash+n) past the boundary; math zones are preserved verbatim. Any new write path that accepts long-form text must call the helper before insert/update — otherwise the render layer can't distinguish "real line break" from "literal text".
- **OMML + math defaults via post-processing.** Two `docx`-library limitations land on the same workaround. (1) `ImportedXmlComponent` wraps imported XML in an `<undefined>` element Word rejects, so we emit placeholder runs and swap them for OMML after `Packer.toBuffer`. (2) The library doesn't expose `<m:mathPr>` for settings.xml, and Word's built-in math defaults (`defJc=centerGroup`, `wrapIndent=1440`, non-zero margins) shift any paragraph containing a 2-D math element (`<m:f>` etc.) ~1″ right of plain-text paragraphs — option `(A) -3/4` ends up out of column with option `(A) -1`. `patchZip` in `src/lib/export/docxBuilder.ts` handles both: marker → OMML in `word/document.xml`, and `<m:mathPr defJc=left wrapIndent=0 lMargin=0 rMargin=0>` injected before `</w:settings>` in `word/settings.xml`.
- **Restart `npm run dev` after adding new routes.** Tailwind JIT can miss files created mid-session. Stop dev, `rm -rf .next`, restart before UI smoke tests.
- **`/notes` LaTeX in body prose only.** Four `SubtopicNote` / `ConceptUnit` fields render as plain text (no KaTeX) AND feed SEO `metadata.description` / JSON-LD where KaTeX would be invalid: `note.title`, `note.oneLineDefinition`, `note.whyItMatters`, `concept.name`. LaTeX in any of these leaks through as raw `\(\hat{i}\)` markup on the page AND in page metadata. **Keep math only in body fields** (`intuition`, `definition`, `formula.latex`, `authoredExample.{prompt,steps,answer}`, `trap.{title,body}`) — those go through `KatexRenderer` correctly. Use Unicode (`î`, `ĵ`, `k̂`, `Σ`, `°`) or plain prose for the four plain-text fields. **Body fields also support `**bold**`** (renders via KatexRenderer / RichText — use it for key terms), and the **`definition` field additionally supports `- ` bullet lists** (rendered by `RichText`): bullet *list-shaped* definitions (term/type/property enumerations), keep narrative ones as prose. The plain-text fields render `**`/`- ` literally — never use them there.
- **Word export: lowercase option labels at render only.** Bank stores `A/B/C/D` uppercase (Excel + DB convention); the `.docx` export renders them as `(a)/(b)/(c)/(d)` in both question paper and answer key (`opt.label.toLowerCase()` in docxBuilder). Browse cards + edit form still show uppercase — only the rendered Word doc is lowercased. If a future surface needs to render bank-style labels, follow the same boundary: lowercase at render, never in the DB.
- **Word export: underline bypasses the math pipeline.** DB convention is `\(\underline{\text{word}}\)` (or `\(\underline{\textit{word}}\)` for italic+underline — biology taxonomy questions). KaTeX renders these in the browser; the docx export detects them via `UNDERLINE_BYPASS_RE` in [src/lib/export/ommlBuilder.ts](src/lib/export/ommlBuilder.ts) and emits a native Word run (`TextRun({ text, underline: { type: "single" }, italics? })`) instead of routing through `temml → mml2omml → <m:borderBox>` — Word doesn't reliably draw the bottom border on inline-math borderBox under our injected math defaults. Trailing punctuation INSIDE the delimiters (`\(\underline{\text{x}}.\)`) is split off into a separate text segment. Any pattern outside the regex (bare `\underline{word}`, chained `\text{}\text{}`, `\textbf` variants, block math) falls through to the OMML pipeline and renders without an underline in Word — run `npm run audit:underlines` after each new English / Biology batch to catch fall-throughs.
- **Tables in question content use GFM pipe-tables (2026-06-02).** A table inside a question `text` or `context` is authored as a standard Github-flavored markdown pipe-table — a header row **plus a `|---|---|` separator row**, then data rows. The separator row is mandatory and is what distinguishes a real table from inline `|·|` math (determinant `\(|A|\)`, abs value `|x|`, cell notation `Zn|Zn²⁺`): a line of pipes with **no** following separator stays prose. `parseTableBlocks` in [src/components/math/parseTableBlocks.ts](src/components/math/parseTableBlocks.ts) (pure, math-masked via `maskMathZones`, TDD in `tests/parse-table-blocks.test.ts`) splits text into prose + table blocks; cells keep their `\(...\)` math and `**bold**`. Rendered by `BlockText` (`src/components/math/BlockText.tsx`) on `/browse` (expanded card only — collapsed preview stays plain `KatexRenderer` so a table can't blow past `line-clamp-2`) + the editor Preview, and as a native Word `<w:tbl>` in `docxBuilder` (the question NUMBER rides on the first paragraph; a stem opening with a table gets a numbered empty paragraph first). **No DB primitive** — it's all in the existing `text`/`context` columns; `normalizeNewlines` is compatible (it upgrades an Excel-authored literal-`\n` table into real newlines). **Future-only**: the existing 13 Statistics (lossless 2-row linearization) + 37 Match-Lists were NOT backfilled — they still render as linearized text. Options don't support tables (v1). For a genuine ≥3-column data grid that can't be a markdown table, fall back to a question image like a diagram.

## Recurring pitfalls

Patterns that have bitten this codebase more than once. Each one earned its place by causing a real production regression — read before writing new code that resembles the shape.

- **PostgREST 1000-row cap on raw `.select()`.** Any `client.from(...).select(...)` that derives a count, a distinct set, a sort, or any aggregate from the *row payload* (rather than response headers via `count: "exact"` or a SQL aggregate via RPC) is suspect once the table can exceed 1000 rows. PostgREST silently truncates at row 1000 — no error, just wrong answers. **Already bit us three times:** dashboard totalQuestions (migration `0018` get_dashboard_stats), PYQ-year filter dropping older years (migration `0019` get_pyq_years), and upload commit dedup races (fixed by switching to `.upsert(..., { onConflict, ignoreDuplicates: true })` — let the DB unique index enforce dedup, not an in-memory `Set`). **Audit checklist before writing any new `.select()`:** (1) Is the row payload itself the answer, or are you computing something from it? (2) If computing, can the underlying table exceed 1000 rows ever (today or as the bank grows)? (3) If yes, use `count: "exact", head: true` for counts, or write a `security invoker` RPC that does the aggregate in Postgres. Never trust a row-derived count from `.select()` past the first 1000 rows.
- **`next dev` is more forgiving than `next start` for server↔client prop serialization.** Functions and other non-serializable values passed from a Server Component to a Client Component compile cleanly under `next dev` but throw at SSR time under `next start` ("Functions cannot be passed directly to Client Components"). This bit us on the 2026-05-13 Pagination revert. **Mitigation:** the pre-push hook in `.githooks/pre-push` runs `next build` before allowing a push, so this class of bug is caught locally rather than after a Vercel deploy. Don't `git push --no-verify` unless you know exactly why.
- **Source-source subtopic name collisions during bulk chapter merges.** When canonicalizing N source chapters into one target chapter, a bulk `UPDATE subtopics SET chapter_id = '<tgt>' WHERE chapter_id IN ('<src1>', '<src2>', ...)` can fail with `23505` on `subtopics_chapter_id_name_key` even if a pre-flight source-vs-target collision check came back clean — because two sources may share a same-named subtopic that collides only once both are reparented. Bit us on the NDA Physics E&M cluster (5 sources → "Magnetic Field Inside a Solenoid" appeared in two of them). **Mitigation:** process sources sequentially via a `DO $$ FOR mapping IN (VALUES (...)) LOOP ... END $$` block; each iteration redirects colliding questions, deletes colliding source subtopics, reparents the rest, updates remaining question chapter_ids, and deletes the source chapter — so by the time source 2 merges, source 1's content is already in target and the standard collision-handling kicks in. Pattern + full template in `[[reclassification-sql-pattern]]`.
- **Catch-all chapters and subtopics drift until you reclassify per-question.** Buckets named "Mechanics", "Physics", "Error Identification in Sentences" collect every question that doesn't cleanly fit a more-specific name. They look harmless during a chapter-level merge but rot the bank's usefulness for technique drills. **Mitigation:** when a chapter or subtopic holds ≤~50 mixed-topic questions, read each stem and produce a `(question_id, target_canonical_id)` mapping; execute as a `DO $$ FOR m IN (VALUES (qid, tgt)) LOOP ... END $$` that (a) looks up the question's source subtopic, (b) finds same-named subtopic in target chapter, (c) redirects+deletes on collision, otherwise reparents+moves chapter_id. Precedents: Spotting Errors 29 q (2026-05-15 NDA English); Mechanics 19 q + Physics 26 q catch-all chapters (2026-05-15 NDA Physics). Beyond ~50 q the user prefers chapter-level merge + subtopic-cleanup as a follow-up pass.
- **`/notes` subtopic slugs are GLOBALLY unique, not chapter-scoped.** `question_concept_tags` keys on `(question_id, subtopic_slug, concept_slug)` with **no chapter or subject column**, and `loadConceptDrills` / the mastery-checkpoint query filter by `subtopic_slug` ALONE. So two chapters that both use a slug like `foundations` will cross-contaminate each other's drill lists + checkpoints. Bit us 2026-05-30: MHT-CET Indefinite Integration reused Sound's `foundations` slug — notes-lint caught it as "DB tag has unknown concept_slug" because the other chapter's concepts don't match. **Mitigation:** every notes subtopic slug must be unique across ALL chapters in `NOTES_CHAPTERS` (the URL segment can repeat per subject route, but the slug used as the concept-tag key cannot). MHT-CET's foundation subtopic was renamed `foundations` → `fundamentals`. notes-lint surfaces the collision but only *after* tags are inserted — pick distinctive slugs up front.
- **Renaming a SHIPPED chapter silently rots its `/guide` + `/notes` cross-refs.** The DB taxonomy and the guide/notes editorial TS are joined only by NAME at request time (`resolveTaxonomy`), so a Phase-D rename/merge leaves the TS pointing at a dead subtopic — the "Drill the N →" CTA resolves to an EMPTY `/browse` filter, no error. Bit us twice on 2026-05-30: the Sound notes 5→4 redesign broke the `/guide/nda-physics` Sound playbook + strategy `mustDrill` + CHAPTER_TABLE prose; the 2026-05-29 Probability merge ("Probability with Dice" → "Probability via Counting") broke two `nda-maths` principle drills + the Probability tier. **Mitigation:** after any rename/merge of a shipped chapter, sync `/guide` `_data` (playbooks `subtopics[]`, strategy `mustDrill`/`skipSubtopics`, principles `drill`, compounds filters, prose counts) + `/notes` `_data` + concept tags, then run `npm test` — the 7 playbook guides + CA themes + Maths each have a `describe.skipIf(!HAS_ENV)` live-taxonomy resolution test (`guide-nda-<subject>-playbooks.test.ts`; `guide-nda-maths-taxonomy.test.ts` for Template A) that fails on drill-target drift. Full procedure: [[shipped-chapter-rename-downstream-sync]]. The `/browse` backlink chip (`getQuestionResources` name lookup) + the single-page Economics chapter CTA are the cross-link surfaces still untested.

## Design axes

Load-bearing design distinctions for the project. Each one earns its place by being structural — getting the axis wrong has cost real work, and the answer to "which axis does this live on?" is non-obvious for the named feature areas.

### Tag taxonomies — principles (horizontal) vs concepts (vertical)

**`/guide` principles** and **`/notes` concepts** are different kinds of tag and must NEVER share a schema or be merged into one taxonomy.

| | Principles | Concepts |
|---|---|---|
| Axis | Horizontal — cross-subtopic | Vertical — within-subtopic |
| Cardinality | ~20 in NDA Maths | ~5–10 per subtopic × hundreds = thousands at scale |
| Storage | TS modules (`/guide/.../principles.ts`) + curated `extraQuestionIds` | DB table `question_concept_tags` (migration 0021) |
| Authoring | Editorial — hand-curated, slow update cadence | Per-upload — admin tagging UI or chat session, fast cadence |
| Value comes from | **Selectivity** (only the top-20, hand-picked) | **Coverage** (every relevant question tagged) |
| Identity question | "What unifying lens does this question demand?" | "What specific technique within this chapter?" |

**The wall — non-negotiable:**
- DON'T migrate `/guide` principles to a DB table. Hand-curation is the signal-to-noise mechanism; "scaling" them dilutes their value.
- DON'T bundle principles into `question_concept_tags` via a `tag_kind` discriminator. Flattens the strategic distinction.
- DO share infrastructure at the seam: one admin tagging UI on `/questions/[id]/edit`, one notes-lint validator, future LLM-suggest can suggest both kinds. Sharing UI ≠ sharing schema.

**Why this earned a section:** The initial concept-tags proposal (Phase 1, 2026-05-17) was a unified `question_tags` table. User pushed back; I conceded. Both axes shipped separately (principles still in TS, concepts in migration 0021) and the wall has held. This section exists so future tag-related features (admin UI, LLM-suggest, AI tutor grounding, MHT_CET_AI integration) don't re-litigate it from scratch.

### Cross-link backlinks — chapter-level (automatic name lookup) vs tag-level (manual DB-tagged override)

The `/browse` QuestionCard chip row (Tier 1 + Tier 1.5, 2026-05-18) renders **two distinct classes of backlink** and the wall between them matters. Same dropdown of chips, two completely different authoring loops and data sources.

| | Chapter-level chips | Tag-level chips |
|---|---|---|
| Examples | "Playbook: Sound" · "Concept notes" | "Lever: Vieta" · "Concept: Weighted Mean" |
| Source | Name-based lookup at render time | DB row in `question_principle_tags` / `question_concept_tags` |
| Authoring cost | **Zero per question** — purely a function of `(exam, subject, chapter, subtopic)` | **Manual per question** — chat tagging session, INSERT with `ON CONFLICT DO NOTHING` |
| Coverage | 100% of questions whose chapter has a guide / subtopic has notes | Only questions explicitly tagged (today: 488 principle tags · 262 concept tags) |
| Failure mode | Silent break when DB chapter renamed (no lint catch yet — see ROADMAP "notes-lint guide-side rename validation") | Silent fallback to generic chip when slug doesn't resolve via `getPrincipleName` / `getConceptName` |
| Override behaviour | The default; renders for all qualifying questions | When present, **replaces** the chapter-level chip for the same axis (more specific wins) |
| Resolver | `getQuestionResources({exam, subject, chapter, subtopic})` in `src/lib/links/questionResources.ts` | `getQuestionResources({...}, tags)` — same function, second arg from `getResourceTagsForQuestions` batch |

**The wall — design intent:**
- DON'T expand the chapter-level lookup to do "fuzzy" matching when a chapter rename happens. The failure mode (chip disappears) is the correct signal — fix the rename, don't paper over the drift.
- DON'T attempt to back-fill tag-level chips from the chapter-level data (e.g. auto-create a `Lever: <chapter-name>` chip when no principle tag exists). That destroys the curated-vs-automatic distinction and floods low-leverage questions with meaningless tag chips.
- DO let tag-level chips quietly fall through to chapter-level chips when the tag's slug doesn't resolve. Better a generic "NDA Maths strategy" chip than a broken `/principles/<unknown-slug>` link.
- DO share infrastructure at the seam: both axes flow through the same `getQuestionResources(input, tags?)` function, both render via the same `<ResourceChip>` component in QuestionCard. The two-tier system is a function-signature distinction (optional second arg) not two separate code paths.

**Why this earned a section:** The 2026-05-18 Tier 1.5 ship added tag-level overrides AFTER the Tier 1 chapter-level chips were in production. The temptation in the moment was to refactor into "one unified backlink table" or to have tag-level chips deduplicate against chapter-level chips. Both ideas are wrong — they conflate two different authoring loops (curated tagging session vs no-touch render-time mapping) and two different coverage shapes (long-tail per-question vs blanket-per-chapter). The split shipped cleanly because the function signature preserved the asymmetry: `tags?` is optional, the resolver short-circuits chapter-level chips when a more-specific tag-chip exists, and untagged questions still get the generic chip — graceful fallback throughout. Sister wall to the tag-taxonomies axis above.

### Guide strand axis — execution-mode (chapter-partitioning) vs tier-style (chapter-tiering)

Within Template B variants, the **strand split** is the strategic axis the strategy page renders against. There are two fundamentally different ways to construct it, and they are NOT interchangeable — picking the wrong one produces a strategy axis that sorts questions by nothing meaningful.

| | Execution-mode strands | Tier-style strands |
|---|---|---|
| Subjects | NDA English (R/Rule/Reason), NDA Chemistry (R/Rule/Calculate), NDA Biology (R/Apply/Verify), NDA Geography (R/Apply/Verify) | NDA History (Cornerstone/Foundation Recall/Quick-Win) |
| Strand semantics | Each strand is a SKILL bucket (recall a fact / apply a rule / trace a mechanism / evaluate a statement). Chapters get grouped into a strand by their dominant execution mode. | Each strand is a STRATEGIC TIER (cornerstone weight / foundation recall / quick-win). Chapters get grouped into a strand by their bank share + %HARD profile. |
| Recall slot | Stable — there's always a Recall strand (named-fact recall is universal in Indian entrance exams). | Stable in spirit (Foundation Recall) but the slot SEMANTICS bent — it now groups chapters by tier, not by execution mode. |
| When to pick | Execution modes PARTITION chapters: one cluster of chapters is 60%+ dominated by one mode, others are 20%- on that mode. | Execution modes are UNIFORM across all chapters (25–45% everywhere) — can't partition. AND/OR one chapter has dominant bank share (40%+) that warrants its own Cornerstone tier. |
| Decision probe | For each candidate mode (recall/rule/apply/verify/calculate/reason/multi-statement/date-anchored), count `q × chapter_spread` AND per-chapter %. Top mode at 60%+ in one cluster = execution-mode strands work. | Top mode is 25–45% of every chapter = uniform = falls back to tier-style. Use bank-share + %HARD per chapter as the partition signal instead. |
| HARD calibration | Strand-level (densest-HARD strand called out — Geography's Apply at 23% avg HARD). | Implicit in the tier-structure — Cornerstone IS the densest-HARD tier by construction (History's Cornerstone = Modern India 34% HARD). |

**The wall — design intent:**
- DON'T force execution-mode strands when modes don't partition. History's multi-statement (70 q × 4 ch · 43% HARD) and date-anchored (61 q × 4 ch · 43% HARD) cut UNIFORMLY across chapters — a Bio/Geo-style R/Apply/Verify split would force lopsided cuts (Recall 44 q : Date 163 q : Verify 53 q if grouped by chapter's dominant mode). The strategy axis would sort by nothing meaningful.
- DON'T force tier-style strands when execution modes DO partition cleanly. English's Vocab/Idioms (Recall) and RC/Cloze (Reason) chapters are genuinely different SKILL types, not just different priorities — a Cornerstone/Foundation/Quick-Win split would lose that information.
- DO let the decision probe pick. Test execution-mode first (Template B default); fall back to tier-style only when modes are uniform.
- DO share infrastructure at the seam: both axes use the same `STRATEGY_STRANDS` data shape (each strand has `id`, `label`, `pitch`, `approach`, `chapters: StrandChapter[]`) and the same strategy-page renderer. The two-axis distinction is in the BUCKET MEANINGS (`PlaybookBucket = "recall" | "apply" | "verify"` for Bio/Geo vs `"cornerstone" | "foundation" | "quickwin"` for History) — same code path, different semantics.

**Why this earned a section:** The 2026-05-19 NDA History ship was the first time Template B's strand axis itself bent. Before History, every Template B variant had bent the second + third SLOTS within an execution-mode axis (Rule→Apply for Bio, Calculate→Verify for Chem) — but the axis itself was always execution-mode. History exposed the next level: when execution modes don't partition chapters at all, the axis itself has to change. The temptation in the moment was to force one of the existing slot-bend patterns onto History (most naturally R/Apply/Verify like Bio + Geo) — that would have shipped a strategy page where students see "Apply chapters" and "Verify chapters" labels but no chapter actually leans either way, sorting by nothing. The tier-style fallback shipped cleanly because the strand data shape was already general (chapters grouped under labelled strands with a pitch + approach) — only the bucket vocabulary changed. Sister wall to the tag-taxonomies + cross-link-backlinks axes above: in all three, the right call is to preserve an asymmetric distinction at the shared seam rather than to flatten for elegance.

## Guide structure templates

Three guide structures have shipped. They serve different bank shapes; a fourth subject's guide should pick from these (or pivot again) by analysing the bank first, not by copying precedent.

### Template A — principles-first (NDA Maths)

Use when the bank has **cross-chapter levers** (one principle spans ≥4 chapters) and **non-flat %HARD** (multiple chapters > 20% HARD).

- **Routes:** landing + `/strategy` (Tier A/B/Skip) + `/principles` (catalog) + `/principles/[slug]` (deep dives) + `/compound-tricks` + `/trends` + `/traps`.
- **Tag infra:** DB-backed `question_<X>_tags` table (today: `question_principle_tags`, migration 0023). Hand-curated TOP_N; counts + %HARD + chapter spread computed live from the tag table at request time.
- **Strategy axis:** %HARD-driven tiering. Chapters with high q-count AND low %HARD = Tier A; high q-count + high %HARD with one drillable subtopic = Tier B cherry-pick; everything else = skip.
- **Editorial data shape:** `OVERVIEW + CHAPTER_TABLE + TIER_A/B + SKIP_LIST + TOP_11 principles + DOMAINS long-tail + COMPOUNDS + DRIFT_ROWS + TRAPS + per-principle DETAILS`.

### Template B — playbooks-first (NDA English, NDA Chemistry, NDA Biology, NDA Geography, NDA History)

Use when the bank has **sealed chapters** (largest cross-chapter lever < ~30 q). Pure Template B also requires **flat %HARD** (≤2 chapters > 15%); the Geography variant relaxes that gate (see "B + non-flat %HARD" below).

- **Routes:** landing + `/strategy` (skill buckets, not tiers) + `/playbooks` (catalog) + `/playbooks/[slug]` (deep dives — one per major subtopic OR one per chapter — see variants below) + `/<subject-specific-page>` (e.g. `/vocab-families` for English, `/common-compounds` for Chemistry) + `/trends` + `/traps`.
- **Tag infra:** NONE. Cross-chapter horizontal axis is too thin to justify a DB table. Drill CTAs use `subtopicIds` or `chapterIds` from `resolveTaxonomy` at request time — same machinery as the maths long-tail DOMAINS principles.
- **Strategy axis:** Skill-type buckets, not %HARD tiers. The middle bucket is the variable slot — pick it from the subject's natural seams:
  - **English** uses Recall (Vocab + Idioms — memorisation) / **Rule** (Errors + Grammar — rule application) / **Reason** (RC + Cloze + Rearrangement + FIB — context-driven).
  - **Chemistry** uses Recall (Carbon + Matter + Industrial + Metals + Hydrogen + Everyday Life + Practical — fact recall) / **Rule** (Atomic Structure + Acids/Bases + Reactions + Bonding — rule application) / **Calculate** (Mole Concept — small numeric strand). Chemistry has no chain-reasoning lever (no analogue of RC author-stance) but does have a small but distinct numeric strand worth surfacing as its own bucket.

### Template D — theme-prep checklist for short-half-life subjects (NDA Current Affairs)

Use when the bank's CONTENT goes stale (specific facts rarely repeat across years) BUT the bank's SHAPES are stable (recurring question types persist even when the specific facts in them rotate). NDA Current Affairs: 180 q · 8 ch · 31 sub · ~10 q/paper · ~40 max marks — multi-route templates would teach students 2017–2025 trivia and call it strategy. Template D is the honest alternative: name the half-life, name the recurring shapes, point at this year's news.

- **The half-life test** (empirical entry criterion): SQL-probe the bank for "year mentioned in question vs paper year". If 80%+ of explicit-year mentions are within 12 months of paper, half-life is short. Cross-check by counting recurrence of named entities (specific exercises / schemes / award winners) across paper-years — if each named entity appears in at most one paper, fact-memorisation has near-zero forward-prep value.
- **The stable-themes counter-test:** before defaulting to no-ship, count subtopics that appear in 5+ years of papers. If ≥6 subtopics meet that threshold and carry ≥40% of bank, the recurring SHAPES are stable enough to anchor a guide even when the FACTS aren't.
- **Strand axis = recurrence strength** (NEW — not skill, not strategic priority): Anchor themes (5+ year recurrence) → Recurring themes (3–4 year recurrence) → Occasional themes (1–2 year recurrence). Strand sizes are uneven by design; the prep-investment asymmetry is the point.
- **Theme cards** (the load-bearing artefact) — each anchor theme card carries: (a) **question SHAPE** — one sentence describing the recurring stem pattern, sourced from real bank stems (durable); (b) **prep CHECKLIST** — 3–6 fact-CATEGORIES to harvest from this year's news (durable directives, the student fills in this year's specific facts from an external compendium); (c) optional **durable-anchors** callout — the small subset of structural facts that genuinely don't rotate (G7 nations, UN agency HQs, ISRO launch-vehicle classes, etc.); (d) **drill BrowseLink** — practises the SHAPE against the bank's historical instances, NOT the facts.
- **Routes:** landing ONLY. No /strategy, no /playbooks, no /trends, no /traps, no /reference-tables, no per-playbook detail pages. Every section lives on the single page, ordered: hero + half-life directive + chapter table + anchor theme cards + recurring themes table + occasional themes chips + test-day plan + drill CTAs + closing rationale.
- **Tag infra:** NONE. Cross-chapter axis impossible — each chapter is a different subject domain (Defence ≠ Sports ≠ Awards). No `question_<X>_tags` table.
- **New components:** NONE. Anchor theme cards render as inline JSX `<article>` (same pattern as nda-economics's inline FYP `<table>`).

- **Sitemap priority 0.6** (vs 0.7 for Economics, 0.8 for full landings) — flags the unusual template shape for crawlers.

### Choosing the template — the analysis script

Before proposing a new guide, run this analysis (SQL probes documented in [[english-guide-structure-diverges]] memory):

0. **Bank-thinness gate.** If avg q/paper < 2 OR total bank < ~50 q OR chapters = 1, no Template A/B/C will produce a non-parody `STRATEGY_HEADLINE`. **Ship a single-page landing instead** (see "Single-page landing" section above). NDA Economics (24 q · 1 ch · 1.5 q/paper · ~6 max marks) is the precedent; NDA Polity (90 q · 4 ch · 5 q/paper · 20 max marks) is the smallest *multi-route* guide and clears the floor. Below that floor, multi-route padding hurts more than it helps.
0a. **Content half-life gate** (run AFTER the thinness gate clears). SQL-probe `regexp_matches(text, '(20[12][0-9])', 'g')` against the bank and compute `(year_mentioned - paper_year)`. If 80%+ of explicit-year mentions are within 12 months of paper AND specific named entities (exercises / schemes / awards) almost never recur across paper-years, the content half-life is too short for a multi-route fact-memorise guide. Counter-test: if ≥6 subtopics appear in 5+ years (stable SHAPES even when FACTS rotate), **ship Template D — Theme-Prep Checklist** (see section above). NDA Current Affairs (180 q · 8 ch · 10 q/paper · 90% within-12-months mention rate · ~zero entity recurrence · 8 anchor themes at 5+ year recurrence) is the precedent.
1. **Chapter mix + %HARD per chapter.** Count chapters at each %HARD tier (>15%, >20%, >25%). Helps separate flat (Template B) from non-flat (A or C).
2. **Cross-chapter principle candidates.** Run keyword surveys for plausible horizontal levers. If the top candidate spans ≥4 chapters AND ≥40 q, **principles axis lives — Template A**. If it spans <4 chapters AND <30 q, **principles axis dead — go to step 3**.
3. **Pick B vs C by %HARD spread + concentration.** Three branches:
   - **≤2 chapters > 15% HARD** → flat — **pure Template B** (English / Chemistry / Biology shapes).
   - **3+ chapters > 15% HARD AND HARD is concentrated in 1–2 subtopics per chapter** (cherry-pick pattern lives) → **Template C** (chapter-playbooks + skill-strand + per-chapter DrillPosture overlay + flat-list page like formulas).
   - **3+ chapters > 15% HARD BUT HARD is diffuse within chapters OR concentrated-but-immovable** (no clean cherry-pick) → **Template B + non-flat %HARD variant** (Geography shape — Template B routes/granularity/subject-specific page, but strand-level %HARD calibration in place of DrillPosture).
4. **Subject-specific page.** Most guides have one (vocab-families for English, formulas for Physics, common-compounds for Chemistry, reference-tables for Biology + Geography, timeline-and-pairs for History). If the subject has a flat-list artefact that doesn't fit a playbook (formula sheet, periodic table chunk, named-acts list, name↔formula reference, named-fact pair table, named-place reference, chronology timeline), it's a candidate. Single-domain artefacts → `CommonCompoundsTable`; multi-domain artefacts → the generic `ReferenceTables` component (pass `clusters` + `guidePath`; per-cluster column headers).
5. **Strand axis — execution-mode vs tier-style.** First test EXECUTION-MODE strands (Template B default, what English/Chem/Bio/Geo do). For each candidate mode (recall / rule / apply / verify / calculate / reason / multi-statement / date-anchored), measure `q × chapter_spread` AND the per-chapter distribution. If a mode dominates ONE chapter cluster (60%+ of one chapter, 20%- of others), execution-mode strands work. If modes are roughly uniform across all chapters (25–45% of every chapter), execution mode CAN'T partition → fall back to **TIER-STYLE strands** (Cornerstone / Foundation Recall / Quick-Win — History's pattern). For execution-mode strands, the Recall slot is universally stable. The SECOND slot is usually Rule but can bend to Apply (Bio + Geo) when no rule-application lever exists. The THIRD slot is most variable — Reason (English), Calculate (Chem Mole), Verify (Bio + Geo multi-statement). For tier-style, the slot semantics are different: Cornerstone = dominant chapter, Foundation Recall = recall-heavy mid-chapters, Quick-Win = low-%HARD / smallest chapter.
6. **Subject's natural seams.** If steps 0–5 don't fit (i.e. bank clears the thinness gate but none of A / B-pure / B-variants / C match), propose a new template (and write a memory documenting it).

## Decisions log

Why behind architectural pivots — saves future-you from "why didn't we just…?".

**Convention:** topical intros (like "Foundations" below) sit at the top. Dated entries are bucketed by month — `### YYYY-MM` per month. When a new month begins, add a new `### YYYY-MM` sub-section above the prior one. **Within a month, entries are ordered newest-first (reverse chronological top-down): a new entry goes at the TOP of its month's block.** Net result: the most recent entry anywhere in the log is the first dated entry a reader sees after the foundations. This lets a reader collapse historical months mentally and focus on what's recent.

### Foundations (M1–M3, 2026-05-08)

The load-bearing choices made during the initial scaffold. Every later phase rests on these — re-litigate only with explicit reason.

- **No Prisma.** Supabase RLS is the security boundary; Prisma uses a single privileged DB user and bypasses RLS by default. Forcing per-request `SET LOCAL` JWT injection fights the tide. `@supabase/supabase-js` carries the user's JWT through naturally.
- **RLS helpers in `private` schema.** PostgREST exposes any `public.*` function as a `/rest/v1/rpc/<name>` endpoint. Supabase advisor flagged `current_user_org_id()` / `current_user_is_admin()` as callable by `anon` and `authenticated`. Functionally safe (returns `null`/`false` for anon) but defence-in-depth — moved to a schema PostgREST doesn't expose.
- **OMML via marker-and-post-process.** The `docx` library's `ImportedXmlComponent.fromXmlString` wraps imported XML in an `<undefined>` element that Word refuses to open. We render placeholder text where math should go, then patch `word/document.xml` after `Packer.toBuffer`. Sidesteps the library quirk; works for arbitrary OMML.
- **Word export = ZIP of two files.** First version was a single .docx with a 3-way layout toggle. User asked to split: a Question Paper distributable without leaking answers, and a separate Answer Key. One ZIP keeps the bundle obvious. **Superseded 2026-05-13** — ZIP killed for mobile UX; route now returns one .docx per request via a required `kind` selector.
- **Hard 200/export cap, no auto-split.** Vercel function timeout is the binding constraint. A clear error ("narrow filters") ships faster than a zip-of-zips. Revisit if a teacher genuinely needs 500 questions in one paper.
- **Chapters/subtopics auto-create, subjects don't.** Subjects are top-level taxonomy curated centrally; auto-creating "Phyiscs" from a typo would corrupt the canonical list. Chapters/subtopics are per-upload working data — small typo cost, and a merge tool can clean up later.

## Notes editorial workflow

Authoring a new chapter of `/notes` content. The loop is locked-in as of the Phase 2 ship (concept drills come from the DB, not TS). Order matters because some steps depend on earlier ones.

### 0. Decide the chapter structure — pedagogy-first, bank is a guide

The chapter's subtopic breakdown and concept order are decided from the **teacher/student point of view**: the content must read as a coherent, logical learning progression (foundations → core method → applications → advanced). **The bank's subtopic taxonomy is a GUIDE, not the organizing principle** — the bank is structured for *drilling/filtering on /browse*, so it tells you *what* is tested and *how much* (coverage + emphasis), NOT how to *sequence the teaching*. It frequently splits one pedagogical idea across several subtopics.

Where the bank's split is finer or differently-cut than the teaching arc, **reshape the bank to match the pedagogy** (Phase D merge/rename per [[reclassification-sql-pattern]]) rather than forcing the notes to mirror an incoherent split. The notes `subtopicName` still maps 1:1 to a DB subtopic (lint + concept-tag constraint), so align the DB subtopics to the pedagogical structure *first*, then author 1:1 against the consolidated set.

Concretely: (1) read the bank — sizes, difficulty mix, year spread, real stems — to learn what to teach + emphasise; (2) design the subtopic list + concept ramp as a teacher would, for coherent progression; (3) if the bank's split doesn't match, merge/rename DB subtopics so the 1:1 mapping lands on coherent teaching units; (4) proceed to step 1. **Precedent (2026-05-29, NDA Probability):** the bank stored dice / coins / balls-and-urns / arrangements as 4 separate subtopics that are pedagogically one idea (classical probability = favourable/total on different props); these were merged into "Probability via Counting" so the notes could teach one coherent "Classical Probability" page instead of four repetitive ones. See [[notes-structure-pedagogy-first]].

### 1. Write the TS module

Under `src/app/notes/<exam>/<chapter>/_data/`:

- `chapter.ts` exports `<CHAPTER>_CHAPTER: ChapterNote` with `chapterName` (must match the canonical DB chapter name exactly), `title`, `intro`, and `subtopicOrder: string[]` of stable subtopic slugs.
- One file per subtopic (`<subtopic-slug>.ts`), exporting a `SubtopicNote` with `subtopicName` (canonical DB name), `title`, `oneLineDefinition`, `whyItMatters`, and `concepts: ConceptUnit[]`. **`ConceptUnit` is a discriminated union** (`kind: "formula" | "reference"` is **required**). Both variants share `slug` (stable identity for DB tags), `name`, `intuition`, `definition`, optional `selfCheckExample` (fresh problem, full solution behind one reveal), optional `practiceSet` (Level 1 mastery reps — ~4 short prompt+answer+method items, authored not bank-derived), optional `visualizationSlug` (a static or interactive SVG diagram — build it under `_components/visualizations/`, add its slug to the `VisualizationSlug` union, and add a `case` in `renderVisualization`; all-SVG, no 3D library — see the `_components/` note above), optional `pyqExampleId` (one featured PYQ), and optional `traps`. Variants differ only on the **core teaching slot**:
  - **`kind: "formula"`** — carries optional `formula?: FormulaSpec` (label + LaTeX + symbol legend) and required `authoredExample` (prompt + step-by-step solution + final answer). Use for technique-driven concepts where the teaching unit is "apply this formula / method to a problem". The pedagogy ramp: intuition → definition → formula? → visualization? → worked example → self-check? → Level-1 practice? → featured PYQ → traps.
  - **`kind: "reference"`** — carries required `table: ReferenceTable` (`columns: string[]` with 2–5 plain-text headers, `rows: ReferenceRow[]` with `cells: string[]` parity-checked against `columns.length`, optional per-row `noteAmber` for amber-tinted callouts, optional per-row `pyqExampleId` for `[Q]` chips, optional table-level `caption`). Use for named-fact recall where the teaching unit is "memorise this table" (frequency bands, transducer chain, ear anatomy, periodic-table-style lookups). The pedagogy ramp: intuition → definition → visualization? → reference table → self-check? → Level-1 practice? → featured PYQ → traps. Self-check + practice on reference variant ARE NOT redundant — they're "spot the wrong row" / "single-row recall" reps.
- **Picking the variant**: read the bank questions for that concept. If the answer hinges on a derivation or formula application → formula. If the answer hinges on memorising a specific named fact ("ultrasonic is > 20 kHz", "cochlea converts pressure to electrical") → reference. A subtopic can (and often should) mix both — Sound's `properties-of-sound-waves` has 2 formula concepts + 1 reference, `sonar-and-ultrasonic` is pure reference, `echo-acoustics-reverberation` is pure formula.
- **Diagrams — selective by decision rule, NOT default-on** (see [[notes-diagram-decision-rule]]). `visualizationSlug` is optional on purpose; a diagram on a non-spatial concept is decorative slop and adds a client-island for no payoff. Real hit-rate even on visual chapters is ~40–60% of concepts (Vectors 17/28, Statistics 12/31, 3D Geometry 6), and ~0% on recall/reference chapters. Per concept, walk the rule: **(1)** Does it have a spatial/geometric mental model? No (formula manipulation, named-fact lookup, counting rule) → no diagram. **(2)** Inherently 3-D (axes, planes, vectors, solids)? → build a **drag-to-rotate turntable** (`makeProject(az, el)` + pointer drag — the Vectors / 3D-Geometry pattern; a fixed projection of a 3-D object is a quiet failure). **(3)** 2-D or a cross-section (triangle, Venn, edge-on tangency)? → **static server-component SVG** (the cross-section is often *clearer* than rotating — e.g. sphere↔plane `p=r`). **(4)** Cap it to the chapter's load-bearing concepts. Add-one mechanics + SVG conventions are in the `_components/` note above.
- **Concept-content alignment — the worked example must teach THIS concept with tools already taught** (see [[notes-concept-content-alignment]]). Every `authoredExample` + `selfCheckExample` must (a) actually illustrate the concept named in the heading, and (b) use only techniques from the **current or earlier** concepts/subtopics in `subtopicOrder` — no forward-reference in the SOLUTION METHOD. The failure mode (shipped twice on Matrices & Determinants): a "scalar multiplication" concept whose worked example was really matrix *multiplication* (taught later); an "evaluate determinants" concept that row-reduced (a property taught two concepts later) AND re-solved its own featured PYQ. Distinctions: a **forward-POINTER** in prose/catalog (stating a consequence the concept exists to deliver, e.g. "skew odd-order ⇒ det 0" before the Determinants subtopic) is **fine**; elementary prior-knowledge (2×2 `ad−bc`) is fine. What's NOT fine is the worked example's *method* needing a not-yet-taught technique when a current-level method exists. Also: the `authoredExample` must be a **different problem from the `pyqExampleId`** (don't solve the same determinant twice), and a `selfCheckExample` shouldn't duplicate another concept's. If a featured/drill PYQ's DOMINANT skill is a later concept, **retag it** to that concept (as `66be5b2d` moved from equality → multiplication), don't teach it early.
  - **Authoring ORDER (prevents the systemic duplication found bank-wide 2026-06-02):** author the worked example FIRST, from scratch, then attach a *different* PYQ as `pyqExampleId` — never reverse-engineer the worked example from the PYQ. The reverse direction is exactly what seeded ~60 "worked example == featured PYQ" duplications across 6 shipped chapters. `npm run notes:lint` now WARNs (heuristically, by number-overlap) when an example re-uses its PYQ's numbers — but it only catches number-heavy cases, so the discipline matters.
  - **Prefer "second real PYQ, worked" over an invented problem when de-duplicating.** A worked example pulled from a *different* tagged bank question is answer-keyed-correct AND distinct — no hand-authored arithmetic to get wrong. Hand-authoring is fine for clean didactic numbers, but **no gate checks arithmetic**: a fresh worked example is only as correct as your verification, whereas a duplicated one was at least provably right. So either re-derive every hand-authored answer independently before ship, or anchor the example to a second real PYQ.
- **Foundations**: prepend a few primitive concepts (no `pyqExampleId`/drill — exempt from notes-lint check 4 **only on formula variant**; reference concepts are never foundations because they are the bucket for the subtopic's flat-fact recall). Give procedural foundations a `practiceSet`; skip it on purely-conceptual ones.
- **Plain-text fields** (`title`, `oneLineDefinition`, `whyItMatters`, `concept.name`, `formula.label`) render WITHOUT KaTeX — use Unicode/prose, no `\(...\)`. `npm run notes:latex` catches leaks.
- **Markup in body fields** (2026-05-29): use `**bold**` for key terms (renders via KatexRenderer / RichText), and in the `definition` field use `- ` line-prefixed **bullets** when the definition is list-shaped (enumerates terms/types/properties) — `RichText` renders them as a `<ul>`. Keep narrative definitions as prose; don't force single statements into bullets. `**`/`- ` are literal in the plain-text fields above — never use them there.
- `index.ts` re-exports the union as `<CHAPTER>_NOTES: Record<slug, SubtopicNote>` and `<CHAPTER>_SLUGS: string[]`.

**No page files to write.** The chapter's `page.tsx` + `[subtopicSlug]/page.tsx` are thin wrappers — clone the Statistics pair, swap the two `getNotesChapterBySlug(...)` args. ALL data-loading + layout lives in the shared `NotesChapterLanding` / `NotesSubtopicPage`.

**The slug is the stable contract** — once a chapter ships, never rename a concept `slug` without a matching UPDATE on `question_concept_tags`. Notes-lint flags orphan slugs as errors but only after they've already broken pages.

### 2. Register in `NOTES_CHAPTERS` (single source of truth)

`src/lib/notes/chapters.ts` is the registry. Append one entry — `{examName, subjectName, subjectRoute, subjectDisplay, chapterSlug, chipLabel, chapter, notes, slugs}` — importing the chapter's `_data` exports. Consumers derive from it automatically: the shared page renderers (`NotesChapterLanding` / `NotesSubtopicPage`), `subtopicSlugRegistry` (concept-tag validation + admin tagging UI), `links/notesIndex` (chip lookups), `links/tagNames` (concept-name lookups), `app/sitemap` (route entries), `/notes/<subjectRoute>/page.tsx` (chapter cards), `scripts/notes-lint` + `scripts/notes-latex-audit` (validation). The only per-chapter files are `_data/*` + the two thin route wrappers.

### 3. Run a chat tagging session

For each chapter, propose a `(question_id, concept_slug)` mapping for every PUBLIC question. Same inline-iteration pattern as the taxonomy cleanup work.

Audit query:
```sql
SELECT q.id, q.difficulty, q.pyq_year, q.set_id, LEFT(q.text, 200) AS text_preview
FROM questions q
WHERE q.chapter_id = '<chapter-uuid>' AND q.visibility = 'PUBLIC'
ORDER BY q.set_id NULLS LAST, q.difficulty, q.pyq_year DESC NULLS LAST;
```

After user approval, INSERT via the standard atomic block:
```sql
INSERT INTO question_concept_tags (question_id, subtopic_slug, concept_slug, tagged_by_llm)
VALUES
  ('<q-uuid>'::uuid, '<subtopic-slug>', '<concept-slug>', true),
  -- ...
ON CONFLICT (question_id, subtopic_slug, concept_slug) DO NOTHING;
```

Mark `tagged_by_llm = true` on LLM-suggested rows so a future admin-review query can find them. The DB row count plus the LLM flag is the audit trail.

### 4. Verify integrity

- `npm run notes:lint` — every `subtopicName` resolves under live taxonomy; every `pyqExampleId` is PUBLIC + in the parent subtopic; every DB tag's `concept_slug` matches a known TS concept (catches typos in either direction); each TS concept has ≥1 DB-tagged question (soft warn for un-tagged concepts); **and (check #5, soft warn) flags when a worked example / self-check re-uses its featured PYQ's distinctive numbers** (the duplication heuristic — number-based, so it catches computational dups and misses word/variable-only ones). Exits non-zero on error; WARNs don't block.
- `npm run notes:latex` — no LaTeX markup in plain-text fields, no unbalanced `\(...\)` / `\[...\]` delimiters. Exits non-zero on either.
- `npm run prepush` — typecheck + lint + build clean.
- **`npm run prepush` covers `npm test`** as of 2026-06-02 (the hook now mirrors CI), so a green pre-push won't red-CI on a test break. Still worth knowing the failure mode: a new notes chapter can flip a literal assertion — `tests/notes-index-helper.test.ts` used "Matrices & Determinants" as a *no-notes* example, which shipping that chapter turned true. Keep negative test cases on synthetic chapter names; real chapters gain notes later ([[prepush-excludes-npm-test]]).
- **Concept-content alignment read-through (manual — not lintable).** `notes:lint` check #5 now auto-WARNs on *number-heavy* worked-example/PYQ duplication, so the manual read-through focuses on what no script catches: (a) the example actually **illustrates the named concept** (not an adjacent one), (b) its method uses only **current/earlier techniques** (no forward-reference per [[notes-concept-content-alignment]]), (c) **word/variable-only** dups the heuristic misses, and (d) **the arithmetic is correct** (a wrong worked example is worse than a duplicated one, and no gate checks math). This caught a misplaced multiplication example on Matrices & Determinants only on a human read of the page. Do it before Ship.

### 5. Ship

ISR-cached `/notes` pages pick up new tags within the 1-hour `revalidate` window. Commit the TS module + the new registry entry; the DB rows are already live from Step 3.

### Invariants to verify before commit

- **Set-sibling co-location**: questions sharing `set_id` (passage groups) MUST be tagged with the same concept(s). Splitting a passage group breaks `/browse` + Word-export grouping. Audit `set_id` groupings in Step 3 before drafting the mapping.
- **`pyqExampleId` stays in TS**: the one editorial "featured" example per concept is hand-picked and lives in the TS module. Drill UUIDs come from the DB — don't reach back to a TS array.
- **Concept slugs are stable IDs**: never edit a `slug` in a published note. If a rename is genuinely necessary, do it as a one-shot `UPDATE question_concept_tags SET concept_slug = '<new>' WHERE subtopic_slug = '<sub>' AND concept_slug = '<old>'` in the same transaction as the TS edit.

See "Design axes" above for why drills live in the DB while pyqExampleIds + concept definitions live in TS — they're on different axes.

## After a new upload

When a new question-batch lands, run the 6-step ritual in order. The upload pipeline is auto (taxonomy auto-creates, `content_hash` dedup, default PUBLIC visibility, live counts in `/browse` + dashboard + `/guide` TOP_11 + `/notes` drills). What's NOT auto and needs this ritual: **tag coverage, taxonomy fragmentation cleanup, and TS-static editorial copy**.

1. **Sanity-check the batch** (always) — confirm `inserted` vs PUBLIC/PRIVATE counts, PYQ metadata stamped, no missing years
2. **Taxonomy delta cleanup** (if ≥5 new subtopic auto-creates or a new chapter name) — Phase D delta inline; don't restart from scratch. Precedent: 2026-05-17 NDA Maths re-Phase-D (~770 new auto-creates closed in one session)
3. **Principle-tag delta survey** (if new questions in TOP_11 chapter footprints) — incremental per-new-chapter, not whole-bank
4. **Concept-tag delta session** (if new questions in `/notes`-covered subtopics) — also revisit dropped-gap ConceptUnits; bank growth can mature what was previously dropped
5. **Editorial copy refresh** (if counts move ≥5–10%) — `whyItMatters`, OVERVIEW constants, CHAPTER_TABLE, strategy %HARD, trends callouts. Mechanical TS edits
6. **Integrity check** (always) — `npm run notes:lint` + `npm run prepush` before commit

Steps 2–5 are conditional and can be deferred / queued across sessions. Full procedure + SQL probes + skip-conditions: [[post-upload-ritual]].

## Operations

Day-to-day knobs and where to look when something goes sideways.

### Monitoring

- **Vercel function logs:** dashboard → Project → Logs. The `/api/export`, `/api/sync/mock`, and `/api/upload/*` route handlers all `console.error` on the catch path; surface there.
- **Vercel Analytics:** dashboard → Project → Analytics. Pageviews + visitor counts. Free tier, cookieless. Frontend errors don't surface here yet — if/when noise picks up, consider Sentry.
- **Supabase logs:** dashboard → Logs → API/Postgres. Useful when an export 500s and you want to see the underlying SQL error.
- **Supabase advisor:** run `mcp__supabase__get_advisors` periodically (or after a migration). Two acceptable lints today: `rls_enabled_no_policy` on `public.rate_limits` (intentional, service-role-only access) and `auth_leaked_password_protection` (Supabase auth setting, can be enabled in dashboard).

### When to upgrade tiers

- **Vercel Hobby (current)** is bounded by ~100 GB-h/month of function execution and ~100 GB of bandwidth. The export endpoint is the heavy hitter — when daily traffic crosses ~500 papers, watch the dashboard's bandwidth meter weekly.
- **Supabase Free (current)** is bounded by 500 MB DB + 1 GB storage egress + 5 GB bandwidth. The public bucket of question images is the egress risk; if egress crosses ~80% of the cap mid-month, plan a Pro upgrade.

### Rate limit visibility

The rate-limit table (Phase D) is service-role only and not exposed to the API. To see who's hitting the limit:
```sql
select bucket, count, window_start
from rate_limits
order by count desc
limit 20;
```
Buckets are formatted `export:anon:<ip>` or `export:user:<user_id>`.

### Rotating SYNC_SHARED_SECRET

No code change needed. Set a new value in:
1. Vercel env vars (Question Bank project) → trigger redeploy
2. MHT_CET_AI's env (whatever variable name its publisher uses) → redeploy

The secret is read at request time via `process.env.SYNC_SHARED_SECRET`, so a redeploy on Question Bank's side picks up the new value immediately. Until both sides match, syncs return 401.

### Billing (Razorpay) — env + going live

### Managing members (admins + teachers)

`/dashboard/members` is the admin UI as of 2026-05-26. Add new admins/teachers with name + email + password + role; reset passwords; change roles; remove members. Last-admin protection + self-protection prevent locking yourself out. The page is admin-only; teachers are redirected to /browse.

```sql
update auth.users

```
Run in the Supabase SQL editor with the service role.

### Flipping visibility on existing questions

The default for new rows is **PUBLIC** (since migration 0022). To take a batch PRIVATE (e.g., a paid-org-only release):
```sql
update questions
set visibility = 'PRIVATE'
where source_file = 'NDA_2024_paper.xlsx';
```
The reverse (flipping PRIVATE → PUBLIC) is rarely needed now since the default is PUBLIC, but the same shape with `set visibility = 'PUBLIC'` still works.

### Setting PYQ year/month/comment for a whole upload

Preferred path: open `/uploads/<jobId>` as the org admin, click **Edit** on the PYQ row, fill any of Year / Month / Comment, save. The PATCH covers all questions linked via `upload_job_id`. For a one-shot SQL backfill (e.g. tagging a batch that was uploaded before Phase A landed):
```sql
update questions
set pyq_year = 2025, pyq_month = 'May', pyq_note = 'Shift I'
where source_file = 'MHT_CET_2025_PCM.xlsx';
```
Use SQL only when you can't reach the upload via the UI (ambiguous `upload_job_id`) — otherwise the UI is auditable.

### Deleting a whole upload

`/uploads/<jobId>` → **Delete upload** removes every question linked via `upload_job_id` (cascades options + question_images via FK), then deletes the storage objects, then deletes the `upload_jobs` row. Pre-0013 questions have `upload_job_id = NULL` and are unreachable via this UI — delete those by `source_file` from SQL if needed:
```sql
delete from questions
where source_file = 'BAD_BATCH.xlsx' and upload_job_id is null;
```
