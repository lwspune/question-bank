**How to apply:** add `solution_errata` plus a `kind` discriminator (`answer_affecting` | `source_defect`); render `answer_affecting` under the revealed answer as a distinct labelled block ("Note on the printed textbook"), and `source_defect` only to staff. Three things to know before starting. (1) **The cost is the classification, not the migration** — `answer-key error` is a reliable marker for 274 rows; the other ~955 have to be read, and getting it wrong in the hiding direction is the one failure that matters. (2) **It is hash-safe** — `solution` is excluded from both dedup hashes, so this is in-place `UPDATE`s with no re-minted ids and no orphaned paper/mock references. (3) **Change the writers in the same pass or it silently regresses** — `apply-errata.ts` and its five sibling pipelines write the bracket into `solution` today, and `errata.ts` currently regex-scrapes it back out of prose; leaving them alone means the next chapter re-introduces the defect, which is the drift this project has recorded twice already.

### `mark-mcq-verify` records a `blind_rederivation` verdict it has no way to know was blind

`scripts/ncert/dump-mcq.ts` correctly withholds `is_correct`, and that is the whole of the tool's protection. It is not enough: on this lane a **whole-chapter agent has already derived those same MCQ answers while transcribing**, so handing it the blind dump makes it compare its answer to its own — agreement is guaranteed, the run cannot go red, and `mark-mcq-verify` then writes a `question_reviews` row claiming the strongest evidence class this repo has. Caught 2026-09-09 and fixed in the *brief* (it now permits exactly one focused verifier, reading only rendered pages, as the sole sub-agent); the *tool* still cannot tell the two situations apart.

**Why:** an overstated review label does not merely misinform a reader — `classifyForReview` keys off `method`, so a false `blind_rederivation` **suppresses the later genuine blind pass**. That is worse than no review at all, and it is the exact failure `question_reviews` was built to make legible. The same session produced the mirror-image case from the other direction: I put a printed key's ANSWER into a chapter agent's prompt, which made its pass non-blind before it began.

**How to apply:** make the tool require what the discipline currently supplies. Options, cheapest first: (a) `mark-mcq-verify` refuses unless the verify file declares a `verifierContext` distinct from the chapter's transcription run, and records the weaker `source_key_crosscheck` when it is not; (b) `dump-mcq` writes a nonce into the dump that only a freshly-spawned verifier can echo back. Either way the rule to encode is the general one — **withholding the key does not create blindness when the same context produced the answer** — and it applies to every pipeline here that has a `dump-mcq`, not only NCERT.
