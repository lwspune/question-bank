## Notes editorial workflow

Authoring a new chapter of `/notes` content. The loop is locked-in as of the Phase 2 ship (concept drills come from the DB, not TS). Order matters because some steps depend on earlier ones.

### 0. Decide the chapter structure — pedagogy-first, bank is a guide

The chapter's subtopic breakdown and concept order are decided from the **teacher/student point of view**: the content must read as a coherent, logical learning progression (foundations → core method → applications → advanced). **The bank's subtopic taxonomy is a GUIDE, not the organizing principle** — the bank is structured for *drilling/filtering on /browse*, so it tells you *what* is tested and *how much* (coverage + emphasis), NOT how to *sequence the teaching*. It frequently splits one pedagogical idea across several subtopics.

Where the bank's split is finer or differently-cut than the teaching arc, **reshape the bank to match the pedagogy** (Phase D merge/rename per [[reclassification-sql-pattern]]) rather than forcing the notes to mirror an incoherent split. The notes `subtopicName` still maps 1:1 to a DB subtopic (lint + concept-tag constraint), so align the DB subtopics to the pedagogical structure *first*, then author 1:1 against the consolidated set.

Concretely: (1) read the bank — sizes, difficulty mix, year spread, real stems **AND the SOLUTIONS** — to learn what to teach + emphasise; **list the distinct solution TECHNIQUES (not just question types) and ensure each maps to a planned concept** — a stem-level read misses technique gaps like "differentiate a determinant" or "variance of natural numbers = (n²−1)/12" that only show up in solutions (both leaked because the chapter was authored from a concept list, not from the solutions). **Read HARD *and* MODERATE solutions** — MODERATE is the largest bucket and is where named shortcuts/formulas actually hide (the 2026-06-07 sweep found 7 gaps, all MODERATE-class: geometric-probability, line-of-intersection = n₁×n₂, MD≈⅘SD, Hermitian, adj(Aᵀ), common-terms-of-two-APs, continued-fraction self-reference; a HARD-only read of those same chapters found ~none). EASY is low-yield (basic methods covered by construction) — leave it to the probe's formula scan; (2) design the subtopic list + concept ramp as a teacher would, for coherent progression; (3) if the bank's split doesn't match, merge/rename DB subtopics so the 1:1 mapping lands on coherent teaching units; (4) proceed to step 1. After authoring, `npm run notes:coverage` (step 4) is the automated backstop for this. **Precedent (2026-05-29, NDA Probability):** the bank stored dice / coins / balls-and-urns / arrangements as 4 separate subtopics that are pedagogically one idea (classical probability = favourable/total on different props); these were merged into "Probability via Counting" so the notes could teach one coherent "Classical Probability" page instead of four repetitive ones. See [[notes-structure-pedagogy-first]].

**(5) Write down the chapter's VOCABULARY ORDER before authoring any concept.** List every term and symbol the chapter uses (`\equiv`, tautology, contingency, contrapositive, dual …) and name the ONE concept that introduces each. A term's introduction must precede every use of it, and the check is cheap at design time and expensive afterwards: on Mathematical Logic the four readings of the last column lived in subtopic 5 while subtopics 1–4 used them throughout, which took a full re-read to find and a new concept to fix. **Definitions that are READINGS of something an earlier block produces belong with that earlier block**, not with the subtopic that exploits them — "tautology" is a property of the last column, so it belongs beside "build the truth table", not beside the algebra that shortcuts it. Where a later subtopic re-teaches an earlier term, say so in its prose ("you met this in block 1 — what is new here is …") so it reads as deepening rather than as a second introduction. `npm run notes:arc` is the automated backstop for this, but it is a backstop: the cheap fix is ordering the vocabulary first.

**MHT-CET Maths chapters — recurring defaults (learned from Indefinite Integration + Differentiation, the only 2 CET-Maths chapters noted so far; both needed a reshape).** Treat these as the starting assumptions for the next CET-Maths chapter, then confirm against the actual bank:
1. **Expect a Phase-D reshape, not reorder-only.** BOTH noted CET-Maths chapters had label-based catch-all subtopics that scatter techniques (Indefinite Integration's `weierstrass`/`u-sub` overloads; Differentiation's 3 catch-alls mixing implicit/log/parametric/differentiability). Default plan = re-carve to coherent teaching subtopics. Contrast NDA Maths, where the bank subtopics are usually already clean (reorder-only).
2. **Reshape is NOT downstream-safe any more — `/guide/mht-cet-maths` shipped 2026-08-22 and is name-keyed.** (This item read "there is NO MHT-CET guide" until 2026-09-25, when the Limits reshape found four guide files and the books registry naming the old subtopics.) After a re-carve, sync ALL of: `guide/mht-cet-maths/_data/playbooks.ts` (card `subtopics[]`, summary, `qCount`/`qPerPaper`/`pctHard`), `strategy.ts` (`mustDrill`/`targetHard`/prose), `mht-cet-maths.ts` (CHAPTER_TABLE `focus`), `playbook-details-*.ts` (`subSkills` — write them 1:1 in the notes order so the chapter can be `ARC_VERIFIED` at birth), and `src/lib/books/registry.ts` (`groupSubtopics`). All are pinned by tests (`guide-mht-cet-maths-playbooks`, `notes-guide-subtopic-order`, `books-registry`), so a missed one fails loudly — but only in `test:prod-contract` for the first and third, which the push gate does not run. Still grep `src/` for the old subtopic names before reshaping (greenfield check) and confirm 0 concept tags.
3. **DB subject name is "Maths", NOT "Mathematics".** `getNotesChapterBySlug("mht-cet-maths", …)` + `subjectName: "Maths"` or `resolveTaxonomy` returns nothing. (Header table calls it "MHT-CET Mathematics" — that's prose, not the DB name.)
4. **Convention is `\log` (natural log), never `\ln`** — matches the CET bank solutions + textbook. (NDA Maths uses `\ln`.)
5. **Slug prefix must NOT collide with the NDA sibling.** NDA owns `diff-`, `ii-`, etc.; CET Differentiation used `cetdiff-`, CET Indefinite Integration used bare/`substitution`. Concept slugs are globally-unique tag keys (mht-cet slug-collision pitfall) — pick a chapter-distinctive prefix up front.
6. **CET Maths is HARD-heavy + ~80% Std-12.** Difficulty mix skews HARD (Differentiation ~45%, Indefinite Integration ~60%) — lean into formula/technique density and "all textbook formulas" coverage. A Std-11 topic (e.g. Sequences & Series) is often too thin in the CET bank to clear the bank-coverage gate — count first; reuse the NDA sibling's notes rather than build a thin CET duplicate ([[mhtcet-sequences-notes-deferred]]).
7. Everything else is the standard workflow: pedagogy-first Step 0, quiz-ready Step 1b, 6-agent parallel batch for a multi-subtopic chapter, 100%-coverage tagging, the Step-4 gate chain, `notes:order`, smoke-test the routes. Precedent files to clone: `src/app/notes/mht-cet-maths/differentiation/_data/`.

### 0b. Many chapters at once: the parallel-agent pipeline (JEE Maths, 2026-09-30)

Used to take JEE Mains Maths from 11 to 27 noted chapters in one session. One chapter done by hand is ~2 hours, 60% of it reading rows and re-deriving keys; with agents a batch of 5 chapters dropped from ~10 hours to ~4, with the same checks. **The rule that keeps quality: agents READ and DRAFT, the main session DECIDES and WRITES.** Only the main session touches the DB, `scripts/jee/papers/*.json`, `chapters.ts`, tags and git, and it re-derives every key change an agent proposes before applying it.

**The loop per chapter** (run several chapters' agents at once; keep ≤ ~9 agents live):

1. **Prep agent (read-only).** Dumps the chapter, reads EVERY row, solves EVERY key as printed, checks the booklet/solution doc, and writes four files under `generated-papers/`: `_fix-jee-<code>.ts` (stem/option fixes, certain MCQ key changes, rewritten solutions — dry-run validated), `_plan-jee-<code>.json` (technique re-cut, validated by `scripts/notes-pipeline/jee/recut.js`), `_tag-jee-<code>.json` (2–3 concepts per page, every row once), `_prep-jee-<code>.md` (key changes with derivations, flawed-as-printed rows, fixes with evidence, featured PYQ per concept, per-page counts, uncertainties). NAT key changes go in the report only (they need a `numericOverrides` edit + `resync`).
2. **Main session: review + apply data.** Re-derive every proposed key change and flawed-row claim yourself (they were right ~90% of the time — the one reversal, 1fc5a93f, was an agent following the stored key over the booklet's own letter-for-digit pattern). Then `sh scripts/notes-pipeline/jee/apply-chapter.sh "<Chapter>" <code>` (applies the spec, re-cuts, deletes emptied subtopics, checks classification sync + dup hashes), set any NAT override, and commit the paper JSONs as `fix(jee): repair <Chapter> rows and re-cut ...` on the chapter's branch.
3. **Draft agent (writes only `src/app/notes/jee-mains-maths/<slug>/_data/`).** Reads the tag json, prep report and dump, reads two finished chapters as models, and writes the page files + `chapter.ts` + `index.ts` with full featured UUIDs from the dump, counts computed by script, every example re-derived, and `npm run typecheck` passing. It may merge a concept under 4 rows (editing the tag json) but touches nothing else.
4. **Main session: review + ship.** Read the chapter intro and at least one page, spot-check examples; copy the route pages from a sibling (`sed`), `python scripts/notes-pipeline/jee/register.py <slug> <CONST> "<Chip>" <AFTER_CONST>`, tag with `scripts/notes-pipeline/jee/tag-chapter.ts` (applies by default), `npm run typecheck` + `notes:latex`, then `sh scripts/notes-pipeline/jee/probe.sh <slug> <intro-filter>` (lint · arc · intro · registry tests incl. `notes-hero-collapsible` — the chapter intro must exceed 260 characters, which short one-page chapters miss · intro-count contract) in the background, fix any warning (usually a worked example that reuses the featured PYQ's numbers), commit `feat(notes): ...`, `npm run seo:dates` and `npm run notes:nav-index` (the nav reads a generated index, not the registry; `tests/notes-nav-index.test.ts` fails until it is current), commit `chore(seo): ...`.
5. **End of batch:** full gate once on the tip (`npm run gate`), docs (ARCHITECTURE line per chapter, CLAUDE.md digest ≤1.2 KB, long form in DECISIONS_HISTORY.md, `npm run docs:budget`), then merge the stacked branches in order (`--no-ff`) and delete them. Do not push.

**Agent contracts that mattered:**
- **A lint 'exam not found' on every page is the DB read failing, not the content** — rerun `notes:lint` alone before touching anything, then rerun the gate.
- **Keep tool output small.** Three agents stalled together ("no progress for 600s") on huge `cat`s; resumed with "read the rows file in chunks of ~150 lines" they finished in minutes. Put that line in every prompt.
- **Specs are written with the Write tool, never a heredoc** (heredocs eat backslashes), as `String.raw` TS.
- **A replacement whose target text already appears in the stem is reported as done by the fix tool** — widen the `from`.
- **Papers whose JSON `notes` say BLIND-derived have no source key**: the stored key came from our own solver and deserves no deference.
- **Stage each reviewed chapter folder by name, never its parent folder,** while other agents are still writing. On IMAT (2026-10-09) `git add <subject>/` swept two half-written chapters into a commit; it had to be reset and redone.
- **Draft prompts must name the plain-text fields** (title, oneLineDefinition, whyItMatters, concept.name — no LaTeX, no `**`), ban `\iff`, forbid reusing the featured PYQ's numbers in the worked example/self-check, and give the chapter intro's required first-sentence shape (a bank fact, not a list of the pages).

**Recurring findings worth checking in any booklet-sourced chapter:** letters printed for digits apply as one mapping per row (a→1, b→2, c→3 — if `f'(a)` is f'(1), then `g(c)` is g(3)); a key can be the NEXT question's answer (8 Apr 2024 Q177/Q178 were shifted by one); a quadratic in eˣ keyed with the product of all roots, non-real ones included; determinant keys that skip dividing by |A|; stems whose missing domain (x ≥ 0) makes the region unbounded — keep the key, say so, never feature it.

**Second run: JEE Chemistry, 20 chapters (2026-09-30).** What it added:
- **Pick the subject with env vars.** Set `JEE_SUBJECT=Chemistry` for dump, apply-chapter and register, and `JEE_ROUTE=jee-mains-chemistry` for probe. Maths is the default.
- **Re-run `fix.ts --apply` after `apply-chapter.sh`.** A fix the DB already holds is reported as "already fixed" and is not written to the paper JSON as an override. The second run records it, and a later `resync` would otherwise undo it.
- **The dump prints option images.** Before this, rows whose options are pictures looked blank, and agents reported graphs as "missing options".
- **Scrambled pictures are common in organic chapters.** The source's option pictures are often split across the stem image and the four option slots, so an option can show half of one choice and half of another. The key letter is usually still right.
  - The fix tool cannot repair this. Write the options as text in the spec (keep the block out of `fixes` until you have viewed the pictures).
  - Then clear the stray `image_url`s with SQL guarded on the exact old paths, and add a line to the paper JSON's `notes` so attach-images never re-attaches them. Older paper files keep `notes` as an object keyed by question number, not a string.
- **Withheld (PRIVATE) rows are invisible to the dump,** so an emptied subtopic can still hold one. Move it by hand, update its `classification` in the paper JSON, then delete the subtopic.
- **`bookOrder.ts` holds positions only for registered chapters** (a test enforces it). Park the others and add each position back when its chapter ships.
- **A subject with no strategy guide:** notes pages link `/guide/<subject>` only when `hasSubjectGuide()` says the guide exists.

**Third run: JEE Physics, 28 chapters (2026-10-01).** What it added:
- **An unregistered chapter folder breaks `next build`.** Its route page calls `getNotesChapterBySlug(...)!`, which is undefined until `register.py` runs. Create route pages only for chapters you will register before the next build or gate.
- **`apply-chapter.sh` warns when classification sync is not 0 after an apply.** A re-cut pass died mid-run once: the DB moved but the paper JSONs did not, and its `tail` hid the error. Re-run the re-cut fix until sync reads 0, or the next resync undoes it.
- **Missing figures become composites, not text.** When a stem names (a)–(d) or figures I and II and the row carries one picture, unzip the others from the source docx (`word/media/imageN`), stack them with `scripts/jee/compose_figures.py` (label the panels when the stem labels them), view the result, then attach with `attach-option-images.ts` using `stem` + `replaceStem` (the current path). Note it in the paper JSON.
- **Ask drafts to say how recent a dropped topic's questions are, from the dump.** Communication Systems (none since 2023), transistors (none since April 2023) and radioactivity (4 of 44 after 2023) each state the year the data shows, not a syllabus claim alone.
- **A featured PYQ must not need a later page's formula.** One draft featured an electron circling inside a solenoid on the Ampère page, which needs T = 2πm/qB from the next page; it was swapped for a plain solenoid row. `notes:arc` does not catch this, so read each page's featured row against what the page has taught.
- **Interrupted agents resume from their transcript:** send the agent's id a message naming the files already written; it finishes the rest.

**Fourth run: CDS English — check every row against its printed page first (2026-10-02).** The source was transcribed from scanned papers, and chapter-sliced prep agents had page-checked only the rows they doubted. An every-row check found 441 defects in 2,400 rows (145 wrong keys, mostly derived from corrupted text: sentences swapped between labels, options from the neighbouring item, parts shifted by one). What changed in the method, so it was faster without being looser:
- **Slice by PAPER, not chapter.** A printed page holds rows of three or four chapters; per-paper agents read each page once. 20 papers ran as 20 agents, ≤9 live.
- **One pass, not two.** The agent writes its answers before opening the keys, then a dry-run-validated fix spec and a 120-line ledger. The main session still re-derives every key change and opens the page image when an option claim is doubtful (2024-1 Q32: the agent read the page right but left the option fix out of its spec).
- **Cheap prechecks point agents at likely defects** (solution letter ≠ key, internal notes, duplicate options, "underlined" directions over a stem with no underline); they are starting points, never a sample.
- **Agents must test every printed option for an ordering key** — one claimed "only (b) keeps Q-S together" when (c) did too and was better.
- **Structural fixes go to the source, then `sync-rows.ts --changed`** moves every affected row in place; it never writes solutions (several are hand-rewritten on purpose). A source passage can be SHORTER than the bank (2024-1): check context before any sync, or the rebuild deletes text.
- **Scratch files need a per-agent prefix** — two agents overwrote each other's `m.txt`.
Tools and briefs: `scripts/notes-pipeline/cds-en/` (README there).

**Tools live in `scripts/notes-pipeline/jee/` (tracked; README there):** `dump.ts`, `read.js`, `list.js`, `qnat.ts`, `src.py`, `fix.ts`, `recut.js`, `del-empty-sub.mts`, `sync-classification.mts`, `duphash.mts`, `tag-chapter.ts`, `apply-chapter.sh`, `register.py`, `probe.sh`. Run them from the repo root. Their WORKING DATA (chapter dumps `_jee_<code>.json`, fix specs `_fix-jee-<code>.ts`, re-cut plans, tag specs) stays in `generated-papers/`, which is gitignored.

### 1. Write the TS module

Under `src/app/notes/<exam>/<chapter>/_data/`:

> **No em dashes in the prose (2026-10-05).** They read as AI-written to this audience. Use a full stop, colon, comma or brackets, and rewrite the sentence rather than swapping in " – " or " -- ". `tests/voice-ratchet.test.ts` fails any file that gains one; `npm run audit:voice -- notes/<route>` lists a chapter's hits.

- `chapter.ts` exports `<CHAPTER>_CHAPTER: ChapterNote` with `chapterName` (must match the canonical DB chapter name exactly), `title`, `intro`, and `subtopicOrder: string[]` of stable subtopic slugs.
- **`intro` — write only what the subtopic CARDS cannot say, and never enumerate them.** The chapter landing renders `subtopicOrder` directly beneath the hero as one card per subtopic, each carrying its `oneLineDefinition` and a **live** PYQ count. An intro that lists "(1) Foundations — … (2) Substitution — …" therefore prints the same information twice, in the same scroll, and the prose copy is the one that rots: MHT-CET Indefinite Integration's hero read "121 PYQs" for 82 days while the card under it printed 159, and its six-movement sentence ran 156 words — one unbroken `<p>`, roughly 35 lines on a phone before the first tappable thing. Keep the judgement the cards have no room for (how dense the chapter is, what kind of work it demands, whether order matters, where the difficulty actually sits) and stop. The corrected intro is 94 words against 218. `npm run notes:intro` reports enumerations, over-long intros and stale counts across the corpus. **Prefer a range or a comparison to a hardcoded count** where the sentence works either way — "one of the densest chapters" cannot go stale; "121 PYQs" can, and 58 of 85 intros state a number.
- One file per subtopic (`<subtopic-slug>.ts`), exporting a `SubtopicNote` with `subtopicName` (canonical DB name), `title`, `oneLineDefinition`, `whyItMatters`, and `concepts: ConceptUnit[]`. **`ConceptUnit` is a discriminated union** (`kind: "formula" | "reference"` is **required**). Both variants share `slug` (stable identity for DB tags), `name`, `intuition`, `definition`, optional `selfCheckExample` (fresh problem, full solution behind one reveal), optional `practiceSet` (Level 1 mastery reps — ~4 short prompt+answer+method items, authored not bank-derived), optional `visualizationSlug` (a static or interactive SVG diagram — build it under `_components/visualizations/`, add its slug to the `VisualizationSlug` union, and add a `case` in `renderVisualization`; all-SVG, no 3D library — see the `_components/` note in [ARCHITECTURE.md](ARCHITECTURE.md)), optional `pyqExampleId` (one featured PYQ), and optional `traps`. Variants differ only on the **core teaching slot**:
  - **`kind: "formula"`** — carries optional `formula?: FormulaSpec` (label + LaTeX + symbol legend) and required `authoredExample` (prompt + step-by-step solution + final answer). Use for technique-driven concepts where the teaching unit is "apply this formula / method to a problem". The pedagogy ramp: intuition → definition → formula? → visualization? → worked example → self-check? → Level-1 practice? → featured PYQ → traps.
  - **`kind: "reference"`** — carries required `table: ReferenceTable` (`columns: string[]` with 2–5 plain-text headers, `rows: ReferenceRow[]` with `cells: string[]` parity-checked against `columns.length`, optional per-row `noteAmber` for amber-tinted callouts, optional per-row `pyqExampleId` for `[Q]` chips, optional table-level `caption`). Use for named-fact recall where the teaching unit is "memorise this table" (frequency bands, transducer chain, ear anatomy, periodic-table-style lookups). The pedagogy ramp: intuition → definition → visualization? → reference table → self-check? → Level-1 practice? → featured PYQ → traps. Self-check + practice on reference variant ARE NOT redundant — they're "spot the wrong row" / "single-row recall" reps.
- **Picking the variant**: read the bank questions for that concept. If the answer hinges on a derivation or formula application → formula. If the answer hinges on memorising a specific named fact ("ultrasonic is > 20 kHz", "cochlea converts pressure to electrical") → reference. A subtopic can (and often should) mix both — Sound's `properties-of-sound-waves` has 2 formula concepts + 1 reference, `sonar-and-ultrasonic` is pure reference, `echo-acoustics-reverberation` is pure formula.
- **Diagrams — selective by decision rule, NOT default-on** (see [[notes-diagram-decision-rule]]). `visualizationSlug` is optional on purpose; a diagram on a non-spatial concept is decorative slop and adds a client-island for no payoff. Real hit-rate even on visual chapters is ~40–60% of concepts (Vectors 17/28, Statistics 12/31, 3D Geometry 6), and ~0% on recall/reference chapters. Per concept, walk the rule: **(1)** Does it have a spatial/geometric mental model? No (formula manipulation, named-fact lookup, counting rule) → no diagram. **(2)** Inherently 3-D (axes, planes, vectors, solids)? → build a **drag-to-rotate turntable** (`makeProject(az, el)` + pointer drag — the Vectors / 3D-Geometry pattern; a fixed projection of a 3-D object is a quiet failure). **(3)** 2-D or a cross-section (triangle, Venn, edge-on tangency)? → **static server-component SVG** (the cross-section is often *clearer* than rotating — e.g. sphere↔plane `p=r`). **(4)** Cap it to the chapter's load-bearing concepts. Add-one mechanics + SVG conventions are in the `_components/` note in [ARCHITECTURE.md](ARCHITECTURE.md).
- **Concept-content alignment — the worked example must teach THIS concept with tools already taught** (see [[notes-concept-content-alignment]]). Every `authoredExample` + `selfCheckExample` must (a) actually illustrate the concept named in the heading, and (b) use only techniques from the **current or earlier** concepts/subtopics in `subtopicOrder` — no forward-reference in the SOLUTION METHOD. The failure mode (shipped twice on Matrices & Determinants): a "scalar multiplication" concept whose worked example was really matrix *multiplication* (taught later); an "evaluate determinants" concept that row-reduced (a property taught two concepts later) AND re-solved its own featured PYQ. Distinctions: a **forward-POINTER** in prose/catalog (stating a consequence the concept exists to deliver, e.g. "skew odd-order ⇒ det 0" before the Determinants subtopic) is **fine**; elementary prior-knowledge (2×2 `ad−bc`) is fine. What's NOT fine is the worked example's *method* needing a not-yet-taught technique when a current-level method exists. Also: the `authoredExample` must be a **different problem from the `pyqExampleId`** (don't solve the same determinant twice), and a `selfCheckExample` shouldn't duplicate another concept's. If a featured/drill PYQ's DOMINANT skill is a later concept, **retag it** to that concept (as `66be5b2d` moved from equality → multiplication), don't teach it early.
  - **Authoring ORDER (prevents the systemic duplication found bank-wide 2026-06-02):** author the worked example FIRST, from scratch, then attach a *different* PYQ as `pyqExampleId` — never reverse-engineer the worked example from the PYQ. The reverse direction is exactly what seeded ~60 "worked example == featured PYQ" duplications across 6 shipped chapters. `npm run notes:lint` now WARNs (heuristically, by number-overlap) when an example re-uses its PYQ's numbers — but it only catches number-heavy cases, so the discipline matters.
  - **THE RULE IS FOUR RUNGS, FOUR DIFFERENT PROBLEMS — and the `selfCheckExample` is the one that slips.** `authoredExample`, `selfCheckExample`, the `practiceSet` reps and the featured PYQ are four separate rungs; if any two are the same problem, the ladder is shorter than it looks and the PYQ stops being a transfer test. The self-check is the easy one to get wrong because it is the rung nearest the PYQ in difficulty. Two further shapes of the same defect, neither of which any gate sees: a worked example that prints the PYQ's **intermediate values** as given data (a rehearsal repeats the *method* with new numbers, not the *numbers* with a different method), and a worked example that demonstrates a **special-case shortcut** while the definition teaches a general method — which leaves the taught method worked zero times. All three shipped in `nda-maths/lines`.
  - **Why the lint was silent on all of it until 2026-09-22:** check #5's `distinctive` guard required a shared number to be ≥5, a decimal, or multi-digit, so it was blind wherever every number in the problem is a small single digit — all of coordinate geometry, much of vectors and probability. It had fired on **0 of 2,455** example↔PYQ pairs in the shipped corpus. It now also warns on an **exactly equal number multiset**, and reports 37. Enumeration labels (`1.` at line start, `(1)` inline) are stripped as indices, like subscripts, or every statement-evaluation concept in NDA Geography reads as a duplicate of its own PYQ.
  - **The full arc checklist — eight defect classes, all of which pass every current gate — is [NOTES_ARC_LEDGER.md](NOTES_ARC_LEDGER.md)**, which also records which chapters have been read end-to-end as a learner would read them. Four of the eight have no probe at all and are found only by reading.
  - **Prefer "second real PYQ, worked" over an invented problem when de-duplicating.** A worked example pulled from a *different* tagged bank question is answer-keyed-correct AND distinct — no hand-authored arithmetic to get wrong. Hand-authoring is fine for clean didactic numbers, but **no gate checks arithmetic**: a fresh worked example is only as correct as your verification, whereas a duplicated one was at least provably right. So either re-derive every hand-authored answer independently before ship, or anchor the example to a second real PYQ.
- **Foundations**: prepend a few primitive concepts (no `pyqExampleId`/drill — exempt from notes-lint check 4 **only on formula variant**; reference concepts are never foundations because they are the bucket for the subtopic's flat-fact recall). Give procedural foundations a `practiceSet`; skip it on purely-conceptual ones.
- **Plain-text fields** (`title`, `oneLineDefinition`, `whyItMatters`, `concept.name`, `formula.label`) render WITHOUT KaTeX — use Unicode/prose, no `\(...\)`. `npm run notes:latex` catches leaks.
- **Where a formula GOES is decided by what reads the field (2026-09-24).** The quiz harvester reads `formula.label` + `formula.latex` and nothing else, so editing a shipped concept's formula box re-flags its verified quiz atoms as stale on the next `quiz:sync`; `definition` bullets, `traps` and `practiceSet` reps do not. So: a one-line fact the chapter's PYQs need (a sibling identity, a closed form, a named prerequisite) is a `definition` bullet or a trap — put it in the concept whose step it completes, not in a new concept; edit a `formula.latex` only when the box itself is wrong or incomplete; and open a NEW ConceptUnit only for a block with its own PYQ cluster (≥ ~5 PYQs or a question TYPE with zero coverage), keyed to a `pyqExampleId` whose bank subtopic you have checked matches, with its cited PYQs tagged. **A result TAUGHT in another chapter is restated in ONE line and cross-linked** via the subtopic's `related: [{label, href: "/notes/<subjectRoute>/<chapterSlug>/<subtopicSlug>"}]` (slugs from that chapter's `index.ts`) — never re-taught, never link-only (a link does not survive time pressure). The 2026-09-24 formula-gap sweep found the borrowed layer — `sin²+cos²=1`, Vieta, `Σk`, `∫xⁿ`, `nCk`, the perpendicularity test — missing in four or five chapters each while TAUGHT in its home; author the prerequisites a chapter's PYQs reach for, not only its own topic.
- **Markup in body fields** (2026-05-29): use `**bold**` for key terms (renders via KatexRenderer / RichText), and in the `definition` field use `- ` line-prefixed **bullets** when the definition is list-shaped (enumerates terms/types/properties) — `RichText` renders them as a `<ul>`. Keep narrative definitions as prose; don't force single statements into bullets. `**`/`- ` are literal in the plain-text fields above — never use them there.
- `index.ts` re-exports the union as `<CHAPTER>_NOTES: Record<slug, SubtopicNote>` and `<CHAPTER>_SLUGS: string[]`.

**No page files to write.** The chapter's `page.tsx` + `[subtopicSlug]/page.tsx` are thin wrappers — clone the Statistics pair, swap the two `getNotesChapterBySlug(...)` args. ALL data-loading + layout lives in the shared `NotesChapterLanding` / `NotesSubtopicPage`.

**The slug is the stable contract** — once a chapter ships, never rename a concept `slug` without a matching UPDATE on `question_concept_tags`. Notes-lint flags orphan slugs as errors but only after they've already broken pages.

### 1b. Author for clean quiz-harvest (avoid downstream rework)

`/notes` is the **Quiz Factory's source** — `quiz:harvest` turns each `ConceptUnit` into MCQ atoms: `formula.latex` → a **formula** atom, each `table` row → a **fact** atom, each `selfCheckExample`/`practiceSet` prompt → a **computation** atom, each `trap` → a **trap** atom. The notes' first job is to TEACH, but a few authoring habits make a concept harvest into a *fair* quiz for free — and skipping them forced real rework on the first 11 quiz chapters (enrich `formula.latex` → re-harvest → re-author distractors → delete + re-assemble the frozen 0035 quiz snapshot). Bake these in **while authoring** — they also improve the notes themselves. Full mechanics: [[quiz-formula-coverage-gap]] + [QUIZ_FACTORY.md](QUIZ_FACTORY.md). This is most of why "pedagogy-first" and "quiz-ready" don't conflict — both want complete, self-contained, correct units.

- **Fill EVERY reference-table cell with a real value — never `—`, blank, or a placeholder.** Each `ReferenceRow` cell becomes a `fact` MCQ option; a dash leaks as a broken distractor (the Human-Physiology "Vitamin K → —" row shipped a broken quiz option, fixed only after a user spot-check). If a fact is genuinely unknown, **drop the row, don't dash it.** This is the **highest-leverage rule for recall chapters** (chemistry, biology) — where the reference variant is the workhorse and nearly every cell is a future quiz answer.
- **Put every recallable formula a concept teaches in `formula.latex`, not buried in `definition` prose or the worked example.** The harvester makes a formula-recall atom ONLY from `formula.latex`; a formula taught only in prose becomes **no atom, silently**, and the chapter's formula theme then looks "done" while missing half its formulas (Trig-Identities carried 15 of ~26). It also renders a fuller formula block for students. **But don't pad:** a *technique / method / criterion* with no memorised equation (substitute-the-point, log-differentiate, balance-the-equation) correctly stays OUT of `formula.latex` — only genuine recallable equations/identities belong there (empirically ~75% of coverage-probe flags are techniques — triage, don't auto-enrich).
- **Author every `selfCheckExample` and `practiceSet` prompt to be SELF-CONTAINED.** They read as a connected sequence under the concept, but the harvester lifts each into a standalone, **shuffled** quiz atom — so no back-references ("the above", "this product", "the same compound", "it"), no dependence on a sibling item's setup, and no criterion-less "which is correct?" stems. Each prompt must stand alone to a cold quiz-taker who sees only that one item. (`quiz:lint` flags offenders, but authoring them right avoids the rewrite-via-`stem`-override.)
- **Make `concept.name` standalone-meaningful** — it becomes the quiz stem ("Which is the formula / fact for `<name>`?"). A pedagogical nickname ("Sieve Inequality", "the magic ratio") is meaningless out of context; name the concept by what it IS.
- **Author `traps` generously — aim for ≥12 self-contained callouts across the chapter** if it's (or will be) quiz-targeted. Each `{title, body}` seeds a "spot the mistake" atom; under 12 there's no Common-Traps quiz, and back-filling later costs a re-harvest + delete/re-assemble. A self-contained trap states the misconception **and** the correct fact without referencing "the previous example."
- **Don't carelessly bundle distinct formulas in one `formula.latex` string.** `\qquad`/`\quad`-joined bundles are SPLIT into one quiz slot per piece (fine — each becomes its own MCQ), but only bundle a genuine one-formula family. **Appending** to a bundle later is index/fingerprint-safe; reordering or inserting silently re-maps already-authored distractors to the wrong formula.

### 2. Register in `NOTES_CHAPTERS` (single source of truth)

`src/lib/notes/chapters.ts` is the registry. Append one entry — `{examName, subjectName, subjectRoute, subjectDisplay, chapterSlug, chipLabel, chapter, notes, slugs}` — importing the chapter's `_data` exports. Consumers derive from it automatically: the shared page renderers (`NotesChapterLanding` / `NotesSubtopicPage`), `subtopicSlugRegistry` (concept-tag validation + admin tagging UI), `links/notesIndex` (chip lookups), `links/tagNames` (concept-name lookups), `app/sitemap` (route entries), `/notes/<subjectRoute>/page.tsx` (chapter cards), `scripts/notes-lint` + `scripts/notes-latex-audit` (validation). The only per-chapter files are `_data/*` + the two thin route wrappers.

**An MHT-CET chapter also needs its textbook position** in `src/lib/notes/bookOrder.ts` (class, chapter number, and the Balbharati chapter it means, read from the "MH State Board" spine in `syllabus_concepts` — never from memory). CET notes are listed and linked in book order, Class XI then XII (decided 2026-09-28); `tests/notes-book-order.test.ts` fails if a CET chapter ships unplaced. Registry position no longer decides a CET chapter's order, so append it anywhere.

### 3. Run a chat tagging session

For each chapter, propose a `(question_id, concept_slug)` mapping for every PUBLIC question. Same inline-iteration pattern as the taxonomy cleanup work.

Audit query:
```sql
SELECT q.id, q.difficulty, q.pyq_year, q.set_id, LEFT(q.text, 200) AS text_preview
FROM questions q
WHERE q.chapter_id = '<chapter-uuid>' AND q.visibility = 'PUBLIC'
ORDER BY q.set_id NULLS LAST, q.difficulty, q.pyq_year DESC NULLS LAST;
```

After user approval, INSERT via the standard atomic block:
```sql
INSERT INTO question_concept_tags (question_id, subtopic_slug, concept_slug, tagged_by_llm)
VALUES
  ('<q-uuid>'::uuid, '<subtopic-slug>', '<concept-slug>', true),
  -- ...
ON CONFLICT (question_id, subtopic_slug, concept_slug) DO NOTHING;
```

Mark `tagged_by_llm = true` on LLM-suggested rows so a future admin-review query can find them. The DB row count plus the LLM flag is the audit trail.

### 4. Verify integrity

- `npm run notes:lint` — every `subtopicName` resolves under live taxonomy; every `pyqExampleId` is PUBLIC + in the parent subtopic; every DB tag's `concept_slug` matches a known TS concept (catches typos in either direction); each TS concept has ≥1 DB-tagged question (soft warn for un-tagged concepts); **and (check #5, soft warn) flags when a worked example / self-check re-uses its featured PYQ's distinctive numbers** (the duplication heuristic — number-based, so it catches computational dups and misses word/variable-only ones). Exits non-zero on error; WARNs don't block.
- **`npm run notes:arc -- <subjectRoute> <chapterSlug> --terms` — the teaching-ARC probe (triage, NOT a gate).** Reads the chapter IN `subtopicOrder` and reports FORWARD REFERENCES: notation used before any concept glosses it, and vocabulary used before the concept that introduces it. **No other gate reads a chapter in order**, so a chapter can promise an arc it does not have and stay green through typecheck + lint + notes:lint + notes:latex + build — which is exactly what MHT-CET Mathematical Logic did until 2026-09-20 (`\equiv` used 40 times, "tautology" 3 times and "contingency" once before any of them was defined). Run it bare (`npm run notes:arc`) for the whole corpus: the default NOTATION class returns ~5 findings across 85 chapters, so a new hit is worth reading. Add `--terms` for the vocabulary class when reviewing ONE chapter (~14/chapter — a review tool, not a standing probe) and `--all` to include same-subtopic foreshadowing. **A hit is a question, not a verdict** — naming a thing before defining it is sometimes right ("we will call this a contingency"); the probe exists so that becomes a decision instead of an accident. See [[notes-teaching-arc-forward-reference]].
- `npm run notes:latex` — no LaTeX markup in plain-text fields, no unbalanced `\(...\)` / `\[...\]` delimiters. Exits non-zero on either.
- **`npm run notes:coverage <subjectRoute> <chapterSlug>` — coverage triage (NOT a gate).** Diffs the math in the chapter's PUBLIC solutions vs its notes bodies; **triage the macro/technique channel** (the high-signal one — a `[d/dx]`/`\binom`/etc. flag means a solution uses a technique the notes may not teach; structural fragments are noisy, skim only). This is how the `(n²−1)/12` variance + differentiate-a-determinant gaps would have been caught at authoring time. Triage every flag to either "covered (notation variant)" or "real gap → add a concept". See [[notes-coverage-probe]].
- **`npm run quiz:coverage <subjectRoute> <chapterSlug>` + `npm run quiz:lint <subjectRoute> <chapterSlug>`** (run only if the chapter is or will be quiz-harvested) — the quiz-readiness backstop for Step 1b. `quiz:coverage` flags concepts that teach a formula in prose but leave `formula.latex` EMPTY + chapters with `<12` traps; `quiz:lint` flags non-self-contained `selfCheckExample`/`practiceSet` stems (back-refs, criterion-less "which is correct?", fragments). Both are **triage, not gates** (~75% of coverage flags are techniques — triage per the rule in Step 1b). Catching these now avoids the harvest → re-author → delete + re-assemble rework. See [[quiz-formula-coverage-gap]] + [QUIZ_FACTORY.md](QUIZ_FACTORY.md).
- `npm run prepush` — typecheck + lint + build clean.
- **`npm run prepush` covers `npm test`** as of 2026-06-02 (the hook now mirrors CI), so a green pre-push won't red-CI on a test break. Still worth knowing the failure mode: a new notes chapter can flip a literal assertion — `tests/notes-index-helper.test.ts` used "Matrices & Determinants" as a *no-notes* example, which shipping that chapter turned true. Keep negative test cases on synthetic chapter names; real chapters gain notes later ([[prepush-excludes-npm-test]]).
- **Concept-content alignment read-through (manual — not lintable).** `notes:lint` check #5 now auto-WARNs on *number-heavy* worked-example/PYQ duplication, so the manual read-through focuses on what no script catches: (a) the example actually **illustrates the named concept** (not an adjacent one), (b) its method uses only **current/earlier techniques** (no forward-reference per [[notes-concept-content-alignment]]), (c) **word/variable-only** dups the heuristic misses, and (d) **the arithmetic is correct** (a wrong worked example is worse than a duplicated one, and no gate checks math). This caught a misplaced multiplication example on Matrices & Determinants only on a human read of the page. Do it before Ship.

### 5. Ship

ISR-cached `/notes` pages pick up new tags within the 1-hour `revalidate` window. Commit the TS module + the new registry entry; the DB rows are already live from Step 3.

**Verify the chapter + diagram counts mechanically — don't hand-count.** Run `npm run stats`; it prints the live `/notes` chapter count (by subject) + `diagrams (visualizations/*.tsx)` count. Use those exact numbers when bumping the header line here and the [[visualizations-status]] memory — the diagram/chapter counts have drifted repeatedly when hand-maintained. (`npm run stats` is also the registry-registration check from Step 4: if the chapter count didn't rise, the `NOTES_CHAPTERS` entry is missing.)

**Then run `npm run notes:order`** (migration 0029) — it copies the chapter's `subtopicOrder` onto `subtopics.order_index` so the new chapter's subtopics render in **teaching order** on /browse (filter sidebar + chapter-scoped question list), not by question-count. It's idempotent and derives purely from `NOTES_CHAPTERS`, so it also re-syncs after a Phase-D re-carve of an already-noted chapter (positions shift). The link is by `subtopicName` → DB name, so the script LOUDLY reports any name drift or any DB subtopic the notes didn't order (which would otherwise sort ahead of its ordered siblings) — fix those before considering the chapter shipped. Chapters without notes keep `order_index` NULL and stay count-desc, untouched.

### Invariants to verify before commit

- **Set-sibling co-location**: questions sharing `set_id` (passage groups) MUST be tagged with the same concept(s). Splitting a passage group breaks `/browse` + Word-export grouping. Audit `set_id` groupings in Step 3 before drafting the mapping. **But `set_id` carries TWO different meanings and only one of them binds this rule** (found on CDS Maths Number System, 2026-09-15): a *shared-premise* set ("Consider the following for the next two items… Let P be the smallest…") is a genuine passage group and MUST be co-located, because the second question is unanswerable without the first's setup. A *shared-rubric* set is not — CDS wraps each ten-question data-sufficiency block in one `set_id` whose `context` is only the instruction "Each item contains a Question followed by two Statements", and those ten questions span the whole syllabus. **The discriminator is mechanical: count the distinct chapters in the set.** A rubric block spans several (the two on this chapter span six chapters each), so co-location is not merely undesirable there but *impossible* — concept tags are scoped inside one subtopic. A premise set spans exactly one. Check `count(distinct chapter)` per `set_id` before deciding, and never force a rubric block into one concept.
- **`pyqExampleId` stays in TS**: the one editorial "featured" example per concept is hand-picked and lives in the TS module. Drill UUIDs come from the DB — don't reach back to a TS array.
- **Concept slugs are stable IDs**: never edit a `slug` in a published note. If a rename is genuinely necessary, do it as a one-shot `UPDATE question_concept_tags SET concept_slug = '<new>' WHERE subtopic_slug = '<sub>' AND concept_slug = '<old>'` in the same transaction as the TS edit.

See "Design axes" above for why drills live in the DB while pyqExampleIds + concept definitions live in TS — they're on different axes.
